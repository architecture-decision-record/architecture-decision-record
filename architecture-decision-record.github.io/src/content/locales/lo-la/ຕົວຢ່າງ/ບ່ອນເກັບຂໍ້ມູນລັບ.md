## ບົດສະຫຼຸບ


### ບັນຫາ

ພວກເຮົາຕ້ອງເກັບຂໍ້ມູນລັບ ເຊັ່ນ ລະຫັດຜ່ານ, ກຸນແຈສ່ວນຕົວ, ໂທເຄັນການພິສູດຢືນຢັນຕົວຕົນ ແລະ ອື່ນໆ.

ຂໍ້ມູນລັບບາງຢ່າງແມ່ນເນັ້ນຜູ້ໃຊ້. ຕົວຢ່າງ ນັກພັດທະນາຂອງພວກເຮົາຢາກສາມາດໃຊ້ໂທລະສັບມືຖືຂອງຕົນເພື່ອຄົ້ນຫາລະຫັດຜ່ານຂອງບໍລິການ.

ຂໍ້ມູນລັບບາງຢ່າງແມ່ນເນັ້ນລະບົບ. ຕົວຢ່າງ ທໍ່ສົ່ງມອບຢ່າງຕໍ່ເນື່ອງຂອງພວກເຮົາຕ້ອງສາມາດຄົ້ນຫາຂໍ້ມູນຢັ້ງຢືນຕົວຕົນສຳລັບການໂຮດຄລາວຂອງພວກເຮົາ.


### ການຕັດສິນໃຈ

Bitwarden ສຳລັບຂໍ້ມູນລັບທີ່ເນັ້ນຜູ້ໃຊ້

Vault ໂດຍ HashiCorp ສຳລັບຂໍ້ມູນລັບທີ່ເນັ້ນລະບົບ.


### ສະຖານະ

ຕັດສິນໃຈແລ້ວ. ພວກເຮົາເປີດຮັບທາງເລືອກໃໝ່ເມື່ອມີອອກມາ.


## ລາຍລະອຽດ


### ສົມມຸດຕິຖານ

ສຳລັບຈຸດປະສົງນີ້ ແລະ ສະຖານະປັດຈຸບັນຂອງພວກເຮົາ ພວກເຮົາໃຫ້ຄຸນຄ່າກັບຄວາມສະດວກທີ່ເນັ້ນຜູ້ໃຊ້ ເຊັ່ນ ແອັບມືຖືທີ່ໃຊ້ງານໄດ້.

  * ພວກເຮົາຢາກຮັບປະກັນການເຂົ້າເຖິງທີ່ໄວ ແລະ ງ່າຍໃນຂະນະເຄື່ອນທີ່ ເຊັ່ນ ສຳລັບນັກພັດທະນາທີ່ເຮັດວິສະວະກຳຄວາມເຊື່ອຖືຂອງລະບົບໃນຂະນະເຝົ້າເວນ.

  * ພວກເຮົາຢາກສາມາດແບ່ງປັນຂໍ້ມູນລັບບາງຢ່າງໃນບັນດາຄົນທີ່ເລືອກ ເຊັ່ນ ທີມ.

ພວກເຮົາບໍ່ໄດ້ພະຍາຍາມແກ້ບັນຫາສຳລັບຜູ້ໃຫ້ບໍລິການລາຍດຽວ ເຊັ່ນ ການເກັບຂໍ້ມູນລັບທັງໝົດສະເພາະໃນ Amazon ຫຼື Azure ຫຼື Google.

ພວກເຮົາບໍ່ຕ້ອງການແນວທາງແບບຊົ່ວຄາວ ເຊັ່ນ "ຈື່ມັນ" ຫຼື "ຂຽນໃສ່ບັນທຶກ" ຫຼື "ຫາວິທີເກັບຂອງຕົນເອງ".

ແບບຈຳລອງຄວາມປອດໄພຂອງພວກເຮົາສຳລັບຈຸດປະສົງນີ້ຍອມຮັບການໃຊ້ຜູ້ຂາຍ COTS ທີ່ມີຊື່ສຽງ ເຊັ່ນ ເຄື່ອງມືຈັດການລະຫັດຜ່ານແບບ SaaS.


### ຂໍ້ຈຳກັດ

ໃນຕອນນີ້ ພວກເຮົາຕ້ອງການບາງຢ່າງທີ່ງ່າຍ ນັ້ນຄື ບໍ່ຕ້ອງຂຽນໂຄ້ດ, ບໍ່ຕ້ອງຕິດຕັ້ງເຊີບເວີ, ບໍ່ຕ້ອງໝັ້ນສັນຍາໃຫຍ່, ບໍ່ຕ້ອງໃຫ້ທຸກຄົນໃຊ້ມາດຕະຖານດຽວກັນ.


### ຈຸດຢືນ

ພວກເຮົາໄດ້ພິຈາລະນາ:

1. ເຄື່ອງມືຈັດການລະຫັດຜ່ານສຳເລັດຮູບທີ່ເນັ້ນຜູ້ໃຊ້: LastPass, 1Password, Bitwarden, Dashlane, KeePass, pass, GPG ແລະ ອື່ນໆ.

2. ເຄື່ອງມືຈັດການລະຫັດຜ່ານ COTS ທີ່ເນັ້ນລະບົບ: AWS KMS, Vault ໂດຍ HashiCorp, EnvKey, Secret Server ໂດຍ Thycotic, Devolutions Password Server, Confidant ໂດຍ Lyft.

3. ແນວທາງທີ່ເນັ້ນການແບ່ງປັນ: ການໃຊ້ເອກະສານ Google ທີ່ແບ່ງປັນ, ຫຼື ຊ່ອງ Slack ທີ່ແບ່ງປັນ, ຫຼື ໂຟນເດີເຄືອຂ່າຍທີ່ແບ່ງປັນ ແລະ ອື່ນໆ.

4. ແນວທາງຊົ່ວຄາວແບບເທັກໂນໂລຢີຕ່ຳ ເຊັ່ນ ການຈື່, ການຂຽນບັນທຶກ ຫຼື ການອາໄສໃຫ້ຜູ້ໃຊ້ແຕ່ລະຄົນຫາວິທີຂອງຕົນເອງ.


### ຂໍ້ໂຕ້ແຍ້ງ

Bitwarden, LastPass, 1Password ແລະ Dashlane ທັງໝົດເປັນຜະລິດຕະພັນສຳເລັດຮູບທາງການຄ້າ.

  * ຄຸນສົມບັດຄ້າຍກັນສຳລັບຜູ້ໃຊ້, ທີມ, ອົງກອນ ແລະ ອື່ນໆ.

  * ຄວາມສາມາດເດັສທັອບສຳລັບ Windows ແລະ Mac ແລະ ຄວາມສາມາດມືຖືສຳລັບ Android ແລະ iOS.

  * ສ່ວນຂະຫຍາຍບຣາວເຊີສຳລັບ Chrome ແລະ Firefox ສຳລັບການຕື່ມຟອມອັດຕະໂນມັດ ແລະ ອື່ນໆ.

Bitwarden ມີສອງຂໍ້ໄດ້ປຽບເໜືອອັນອື່ນ:

  * Bitwarden ເປັນຊອດເປີດ ເຊິ່ງໝາຍຄວາມວ່າຄວາມປອດໄພສາມາດຖືກທົບທວນໂດຍເພື່ອນຮ່ວມວິຊາຊີບ ແລະ ບໍລິສັດຍັງເປັນທີ່ຊື່ນຊົມຢ່າງກວ້າງຂວາງຈາກນັກພັດທະນາທີ່ເນັ້ນຄວາມປອດໄພ.

  * ເລື່ອງເລົ່າຈາກຜູ້ເຮັດວຽກດ້ານຊອບແວອະທິບາຍເຖິງຄວາມມັກ Bitwarden ເໜືອອັນອື່ນຢ່າງຫຼວງຫຼາຍ.

ຕົວຢ່າງບົດຂຽນທີ່ດີທົ່ວໄປ: https://jcs.org/2017/11/17/bitwarden

ເວັບໄຊລົງຄະແນນແບບຄູ່ກັນທົ່ວໄປ: https://stackshare.io/stackups/bitwarden-vs-dashlane

ພວກເຮົາເລື່ອນ KeyPass, pass, GPG ແລະ ອື່ນໆ ເພາະມີຄວາມຊັບຊ້ອນເພີ່ມເຕີມ. ທັງໝົດເຫຼົ່ານີ້ເບິ່ງຄືວິທີແກ້ໄຂທີ່ດີສຳລັບຜູ້ໃຊ້ດ້ານເຕັກນິກ. GPG ເບິ່ງດີເປັນພິເສດສຳລັບຜູ້ໃຊ້ດ້ານເຕັກນິກທີ່ຕ້ອງການຄວາມສາມາດທີ່ເນັ້ນຄຳສັ່ງຂ້າມລະບົບ.

ພວກເຮົາເລື່ອນ KMS ເພາະມັນຕິດຢູ່ກັບຜູ້ໃຫ້ບໍລິການລາຍດຽວ.

ພວກເຮົາເລືອກ Vault ສຳລັບຄວາມຕ້ອງການທີ່ເນັ້ນລະບົບ ເພາະຄຳວິຈານສ່ວນໃຫຍ່ເປັນບວກຢ່າງໜ້າອັດສະຈັນ ແລະ ເພາະ HashiCorp ມີປະຫວັດທີ່ດີເລີດສຳລັບຊອບແວ ແລະ ການສະໜັບສະໜູນຄຸນນະພາບສູງສຸດ.

ພວກເຮົາຄັດຄ້ານແນວທາງການແບ່ງປັນ ເຊັ່ນ ຜ່ານເອກະສານທີ່ແບ່ງປັນ, ຊ່ອງທີ່ແບ່ງປັນ, ໂຟນເດີເຄືອຂ່າຍທີ່ແບ່ງປັນ ແລະ ອື່ນໆ. ສິ່ງເຫຼົ່ານີ້ບໍ່ໃຫ້ຄຸນນະພາບດ້ານຄວາມປອດໄພທີ່ພວກເຮົາຕ້ອງການ.

ພວກເຮົາຄັດຄ້ານແນວທາງຊົ່ວຄາວແບບເທັກໂນໂລຢີຕ່ຳ ເພາະພວກເຮົາທຸກຄົນເຫັນດີວ່າມັນບໍ່ແມ່ນເສັ້ນທາງໄປຂ້າງໜ້າໃນໄລຍະຍາວ.


### ຜົນໄດ້ຮັບ

ນັກພັດທະນາອາດຕ້ອງຕິດຕາມຂໍ້ມູນລັບໃນສອງບ່ອນ: Bitwarden ສຳລັບການເຂົ້າເຖິງທີ່ເນັ້ນຜູ້ໃຊ້ ແລະ Vault ສຳລັບການເຂົ້າເຖິງທີ່ເນັ້ນລະບົບ.


## ທີ່ກ່ຽວຂ້ອງ


### ການຕັດສິນໃຈທີ່ກ່ຽວຂ້ອງ

ການຕັດສິນໃຈວ່າຈະໃຊ້ເຊີບເວີ CI/CD ໃດຕ້ອງລວມຫຼັກຖານຄວາມສາມາດໃນການເຂົ້າເຖິງຂໍ້ມູນລັບ.

ພວກເຮົາຈະຕ້ອງຕັດສິນໃຈວິທີຈັດການຂໍ້ມູນລັບ ໃນແງ່ຂອງນະໂຍບາຍ, ການໝູນວຽນ, ອົງກອນ ແລະ ອື່ນໆ.


### ຄວາມຕ້ອງການທີ່ກ່ຽວຂ້ອງ

ຂໍ້ມູນລັບຈະມີຄວາມຕ້ອງການທີ່ກ່ຽວຂ້ອງສຳລັບການປະຕິບັດຕາມກົດລະບຽບ, ການກວດສອບ ແລະ ການຮັບເຂົ້າ/ອອກຂອງພະນັກງານຝ່າຍຊັບພະຍາກອນມະນຸດ.


### ຜະລິດຕະພັນທີ່ກ່ຽວຂ້ອງ

ພວກເຮົາຄາດວ່າພວກເຮົາອາດສົ່ງອອກຂໍ້ມູນລັບບາງຢ່າງໄປເປັນຕົວແປສະພາບແວດລ້ອມ.


### ຫຼັກການທີ່ກ່ຽວຂ້ອງ

ຍ້ອນກັບໄດ້ງ່າຍ.

ຂະໜານກັນໄດ້ງ່າຍ ນັ້ນຄື ງ່າຍທີ່ຈະໃຊ້ເຄື່ອງມືຈັດການລະຫັດຜ່ານຫຼາກຫຼາຍ.

ລອງໄດ້ຖືກ ນັ້ນຄື ມີທົດລອງໃຊ້ຟຣີ ແລະ ບໍ່ມີການໝັ້ນສັນຍາ.


## ໝາຍເຫດ

ໝາຍເຫດການປະເມີນຢູ່ນີ້. ໝາຍເຫດທັງໝົດເປັນຄວາມຄິດເຫັນສາທາລະນະໃນເວທີສົນທະນາ devops ຕ່າງໆ.


### Vault ໂດຍ HashiCorp

Vault ແມ່ນສິ່ງທີ່ທ່ານຕ້ອງການຢູ່ນີ້ຢ່າງແທ້ຈິງ. 

ແຕ່ຢ່າພຽງແຕ່ໂຍນ Vault ເຂົ້າສູ່ການໃຊ້ງານຈິງ ໃຫ້ຕັ້ງມັນໃນສະພາບແວດລ້ອມທົດສອບກ່ອນ ເພາະເອກະສານຂອງ HashiCorp ອາດຂາດຫຼາຍ ເຖິງແມ່ນຜະລິດຕະພັນຂອງພວກເຂົາຈະດີຫຼາຍ.

ເສັ້ນໂຄ້ງການຮຽນຮູ້ຊັນຫຼາຍ ແລະ ການຕັ້ງຄ່າບໍ່ແມ່ນເລື່ອງເລັກນ້ອຍ. 

ການຕັ້ງຄ່າເບື້ອງຕົ້ນຫຍຸ້ງຍາກໜ້ອຍໜຶ່ງ. ແຕ່ຄຸ້ມຄ່າ ແລະ ຊຸມຊົນຈະສະໜັບສະໜູນພຽງພໍໃຫ້ທ່ານຜ່ານໄປໄດ້.

ເອກະສານແຍ່ແຕ່ມີຄູ່ມືອອນລາຍຫຼາຍຢ່າງຂອງຄົນທີ່ຕັ້ງມັນ ແລະ ຖ້າທ່ານເອົາບາງອັນມາລວມກັນ ທ່ານຈະມີການຕັ້ງຄ່າທີ່ໃຊ້ງານໄດ້.

ການຕັ້ງຄ່າເບື້ອງຕົ້ນຕ້ອງລອງຜິດລອງຖືກກັບ helm charts ຂອງພວກເຂົາ (vault ແລະ consul). ເຖິງແມ່ນທາງເທັກນິກທ່ານສາມາດໃຊ້ back-end ອື່ນໆຫຼາຍຢ່າງ ແຕ່ຂ້ອຍບໍ່ແນະນຳເລີຍ. back-end/consul ສາມາດນ້ອຍຈ້ອຍໄດ້ຖ້າທ່ານບໍ່ມີຂໍ້ມູນຫຼາຍທີ່ຕ້ອງເກັບ.

ໃຫ້ແນ່ໃຈວ່າທ່ານຄຸ້ນເຄີຍກັບການໃຊ້ CLI ເພາະ GUI ຄ້າຍກັບພອດທັນໂຄສະນາ/ພິສູດແນວຄິດສຳລັບເວີຊັນ enterprise ຂອງພວກເຂົາຫຼາຍກວ່າ.

ຄວາມຈິງທີ່ວ່າທ່ານບໍ່ສາມາດ "ຕື່ມໃຫ້ເຕັມ" ໄດ້ເປັນຄວາມລຳບາກ. ຕົວຢ່າງ ຖ້າທ່ານມີ 5 ຟິວ ທ່ານຕ້ອງເພີ່ມແຕ່ລະຟິວດ້ວຍມືສຳລັບແຕ່ລະລາຍການ. ສະນັ້ນມັນບໍ່ແມ່ນວ່າທ່ານກຳນົດຟິວລ່ວງໜ້າສຳລັບໝວດສະເພາະ ແລ້ວຕື່ມຟິວເຫຼົ່ານັ້ນສຳລັບທຸກລາຍການໃນໝວດນັ້ນ ມັນຄ້າຍກັບ "ທ່ານສ້າງທຸກຢ່າງທຸກຄັ້ງ" ຫຼາຍກວ່າ ເຊິ່ງ (ໃນຄວາມຄິດຂອງຂ້ອຍ) ເປັນຄວາມລຳບາກຢ່າງຍິ່ງ.

ທ່ານອາດຢາກເບິ່ງ goldfish ເປັນ UI ເທິງ vault ດ້ວຍ. ມັນເຮັດໃຫ້ງ່າຍຂຶ້ນທີ່ຈະນຳທີມຂອງທ່ານມາໃຊ້ມັນ. ພວກເຂົາຍັງມີການສາທິດ. 1. ຕັ້ງ consul. 2. ຕັ້ງ vault ໃຫ້ຊີ້ໄປຫາ consul. 3. ຕັ້ງ goldfish ໃຫ້ຊີ້ໄປຫາ vault. 3. ຕັ້ງ cron job ເພື່ອດຳເນີນ consul snapshot ສຳລັບການສຳຮອງຂໍ້ມູນ.



### LastPass

LastPass Teams. ພວກເຮົາໃຊ້ມັນ ມີແມ່ແບບກຳນົດເອງ, ACL ແລະ ໃນຄວາມເຫັນຂອງຂ້ອຍບໍ່ຂາດຫຍັງ.

ຂ້ອຍໄດ້ນຳໃຊ້ LastPass ໃນອົງກອນຂອງຂ້ອຍ ແລະ ໃຫ້ເກຣດ C+/B-. ບັນຫາໃຫຍ່ທີ່ສຸດໃນຕອນນີ້ແມ່ນຂາດຄວາມເຊື່ອຖືໄດ້. ໃນ 90 ວັນທີ່ຜ່ານມາ ມີຫຼາຍຊົ່ວໂມງທີ່ vault ຖືກບັງຄັບເຂົ້າສູ່ໂໝດອອບລາຍ. ນີ້ບໍ່ດີສຳລັບອົງກອນຂອງຂ້ອຍ ເພາະມີຢ່າງແທ້ຈິງ 4,000+ ລະຫັດຜ່ານທີ່ເກັບຢູ່ໃນ 20+ ໂຟນເດີທີ່ແບ່ງປັນ. ດັ່ງທີ່ທ່ານຈິນຕະນາການໄດ້ ກັບລະຫັດຜ່ານຫຼາຍຂະໜາດນັ້ນ ຢ່າງໜ້ອຍບາງອັນຖືກອັບເດດ ຫຼື ເພີ່ມທຸກວັນ. ພວກເຮົາມີແຜນ DR ຖ້າບັນຫາດຳເນີນເກີນໜຶ່ງຫຼືສອງຊົ່ວໂມງ: ສະຄຣິບລົງລາຍເຊັນ ແລະ ເຂົ້າລະຫັດ CSV dump ຂອງ vault ທຸກຄືນ ທີ່ສາມາດນຳເຂົ້າໃນ keepass.

LastPass ມີການບໍລິການຖົດຖອຍຊົ່ວຄາວທີ່ບໍ່ໄດ້ລາຍງານເປັນບາງຄັ້ງ: ການເຂົ້າສູ່ລະບົບ 'ໃຊ້ໄດ້' ແຕ່ບໍ່ດຶງເວັບໄຊ, ຄຸນສົມບັດແບບສຸ່ມເສຍໃນແຜງຄວບຄຸມຜູ້ບໍລິຫານ ແລະ ບໍ່ແບ່ງປັນກຸນແຈຢ່າງຖືກຕ້ອງສຳລັບໂຟນເດີທີ່ແບ່ງປັນລະດັບສູງສຸດໃໝ່. ຂ້ອຍມີຜູ້ໃຊ້ 'key push'/ສຳຮອງສະເພາະທີ່ຢູ່ໃນທຸກກຸ່ມ. ປົກກະຕິການເຂົ້າສູ່ລະບົບເປັນຜູ້ໃຊ້ນັ້ນຈະແກ້ບັນຫາການແບ່ງປັນກຸນແຈໃດໆ ແຕ່ບໍ່ແມ່ນເມື່ອບໍລິການຖືກທຳລາຍ ເຖິງແມ່ນໜ້າສະຖານະຈະບອກແນວໃດ...

ສຳລັບການລວມ ມັນສາມາດງ່າຍຖ້າທ່ານມີ ACL ທີ່ຖືກຕ້ອງດ້ວຍແບບຈຳລອງສິດໜ້ອຍທີ່ສຸດ ເຊັ່ນ ຖ້າຜູ້ໃຊ້ມີທັງອ່ານ ແລະ ຂຽນ ແລະ ອ່ານຢ່າງດຽວໃນລາຍການ ຫຼື ໂຟນເດີ ພວກເຂົາຈະໄດ້ສິດອ່ານຢ່າງດຽວເທົ່ານັ້ນ. ໂຊກບໍ່ດີ ACL ຂອງອົງກອນຂ້ອຍບໍ່ດີທີ່ສຸດ ສະນັ້ນຂ້ອຍຈຶ່ງໃຊ້ JSON provisioning API ແລະ python ປະມານ 500 ແຖວ ເນື່ອງຈາກລັກສະນະທີ່ຂຶ້ນກັບກັນຂອງ ACL ຫຼາຍຮ້ອຍອັນຂອງພວກເຮົາທີ່ບໍ່ແຜນທີ່ໄດ້ດີກັບແບບຈຳລອງສິດໜ້ອຍທີ່ສຸດ. ສຸດທ້າຍຂ້ອຍໄດ້ ACL ທັງໝົດທີ່ຜູ້ໃຊ້ຢູ່ ແລະ ເຮັດການຍ່າງຕາມຄວາມຂຶ້ນກັນຂອງບາງຢ່າງ.

ຖ້າໂຄງສ້າງ ACL ຫຼື ກຸ່ມຂອງທ່ານຖືກສ້າງດ້ວຍແນວຄິດສິດໜ້ອຍທີ່ສຸດຢູ່ແລ້ວ ເຄື່ອງມືຊິງຄ໌ AD/LDAP ສຳລັບ Windows ຈະເຮັດວຽກໄດ້ດີ.

ຕິດຕໍ່ທີມຂາຍຂອງພວກເຂົາ ແລະ ພວກເຂົາສາມາດຈັດໃຫ້ທ່ານມີການທົດລອງ Enterprise ທີ່ຍາວກວ່າ. ໃຫ້ແນ່ໃຈວ່າທ່ານເຂົ້າໃຈຂໍ້ຈຳກັດຂອງມັນຢ່າງເຕັມທີ່ກ່ອນຕັດສິນໃຈ. ພວກເຮົາມີຄວາມເຈັບປວດຈາກການເຕີບໃຫຍ່ຈຳນວນໜຶ່ງ ແຕ່ນອກຈາກການຢຸດເຮັດວຽກ ຫຼື ຄວາມບົກຜ່ອງຝັ່ງເຊີບເວີແລ້ວ ມັນລຽບລື່ນຫຼາຍ.


### Bitwarden

Bitwarden ມີເຄື່ອງມືອ້ອມຮອບທີ່ດີ (WebUI, CLI, ມືຖື, ເດັສທັອບ). ໂຮດເອງໄດ້ ແລະ ຕັ້ງຄ່າຄ່ອນຂ້າງງ່າຍ. ເອກະສານຄ່ອນຂ້າງດີ ແລະ ເປັນເຄື່ອງມືທີ່ PrivacyTools ແນະນຳ.


### EnvKey

https://www.envkey.com/ ເປັນ saas. ປະຕິບັດ, ລວມ ແລະ ຈັດການໄດ້ງ່າຍຫຼາຍ.

ຄຸນສົມບັດ:

  * ປົກປ້ອງກຸນແຈ API ແລະ ຂໍ້ມູນຢັ້ງຢືນຕົວຕົນ.
