## សង្ខេប


### បញ្ហា

យើងចង់ប្រើ devops ដើម្បី build រួមបញ្ចូល ដាក់ពង្រាយ និងបង្ហោះគម្រោងរបស់យើង។ យើងកំពុងពិចារណា Microsoft Azure DevOps។

  * យើងចង់ឱ្យបទពិសោធន៍អ្នកអភិវឌ្ឍន៍លឿន និងអាចទុកចិត្តបាន ទាំងសម្រាប់ការដំឡើង devops ឧ. ការកំណត់រចនាសម្ព័ន្ធ ព្រមទាំងការប្រើប្រាស់ជាបន្តបន្ទាប់ ឧ. ពេលវេលា build លឿន។
  
  * យើងចង់ពិចារណាប្រើ Microsoft Azure ទាំងមូល សម្រាប់បង្ហោះកម្មវិធីគម្រោង មូលដ្ឋានទិន្នន័យ ។ល។


### ការសម្រេចចិត្ត

បានសម្រេចមិនជ្រើស Microsoft Azure DevOps។


### ស្ថានភាព

បានសម្រេច។ បើកចំហក្នុងការពិនិត្យឡើងវិញ ប្រសិនបើ/នៅពេលដែលព័ត៌មានសំខាន់ថ្មីមកដល់។


## ព័ត៌មានលម្អិត


### ការសន្មត់

ការសន្មត់ devops ធម្មតាទាំងអស់ ដូចជានៅក្នុងសៀវភៅ Accelerate។

  * ការ build លឿនជាជំនួយយ៉ាងសំខាន់។ នេះបង្កើនល្បឿនរង្វិលមតិកែលម្អ។

  * យើងអាចដូរចូល/ចេញផ្នែកពីអ្នកលក់ជំនួស ពោលគឺយើងអាចចង់នាំយកម៉ាស៊ីនមេ build ល្បឿនខ្ពស់របស់យើងផ្ទាល់ ឬប្រើជម្រើសប្រព័ន្ធត្រួតពិនិត្យកំណែរបស់យើងផ្ទាល់ ឬសម្របសម្រួលជាមួយម៉ាស៊ីនមេរួមបញ្ចូលជាបន្តបន្ទាប់ដែលបង្ហោះដោយខ្លួនឯង។
  
  * ភាពងាយប្រើដែលសម្រួលជាជំនួយយ៉ាងសំខាន់ សម្រាប់បទពិសោធន៍អ្នកអភិវឌ្ឍន៍ ហើយបន្តសម្រាប់ផ្នែកស្រាលៗដូចជាភាពស៊ីសង្វាក់ ភាពច្បាស់លាស់ សុវត្ថិភាព និងភាពងាយនៃខ្សែកោងរៀន។

  * នៅពេលអ្វីមួយខូច ឬមានបញ្ហា យើងចង់បានវិធីមានប្រសិទ្ធភាពក្នុងការរាយការណ៍បញ្ហា។ នេះសំខាន់ជាពិសេសសម្រាប់បញ្ហាទាក់ទងនឹងសុវត្ថិភាព។


### ឧបសគ្គ

មិនស្គាល់។ Azure មានការប្តេជ្ញាចិត្តដែលបានផ្សព្វផ្សាយក្នុងការធ្វើការបានល្អជាមួយឧបករណ៍ខាងក្រៅ។


### ជំហរ

យើងបានពិចារណាប្រើ Microsoft Azure Devops ប្រៀបធៀប AWS ដែលជាអ្នកកាន់តំណែង។

យើងបានពិសោធជាមួយ Azure DevOps, Azure Pipelines, Azure Repo និងការបង្កើតម៉ាស៊ីនមេថ្មីរបស់ Azure តាមរយៈ Terraform។

យើងបានពិសោធការទទួលបានជំនួយពីតំណាង Microsoft។

យើងបានប្រមូលព័ត៌មានពីមិត្តភក្តិនៅលើប្លក់ និង Hacker News។


### អាគុយម៉ង់

Azure DevOps ផ្សព្វផ្សាយសំណុំផលិតផលដ៏ល្អឥតខ្ចោះ ប៉ុន្តែពួកវាមិនស្របតាមការអះអាង ហើយមិនដំណើរការល្អជាមួយគ្នា ហើយការគាំទ្រគឺអន់។

បទពិសោធន៍ផ្ទាល់របស់យើង៖

  * ការដំឡើង Azure គឺជាភាពច្របូកច្របល់នៃ UI ដែលខ្លះត្រួតស៊ីគ្នាជាមួយគណនី Microsoft ហើយខ្លះមិនត្រួតស៊ីទេ។ ឧទាហរណ៍ មានការចូល Azure ការចូល Microsoft.com ការចូល Live.com ។ល។ ហើយទាំងអស់កំពុងដំណើរការក្នុងពេលតែមួយ។

  * យើងបានជួបបញ្ហាសុវត្ថិភាពតូចមួយក្នុងអំឡុងពេលដំឡើង ហើយមិនឃើញដំណោះស្រាយទេ។ យើងបានព្យាយាមរាយការណ៍វាតាមវិធីជាច្រើន ទៅកាន់តំណាង Microsoft ជាច្រើន ដោយមិនជោគជ័យ។ យើងបានរាយការណ៍ទៅផ្នែកសុវត្ថិភាព Microsoft ដោយជោគជ័យ ដែលបានឆ្លើយតបថា won't fix។

  * ឯកសារជារឿយៗខុស ឬហួសសម័យ។ យ៉ាងហោចណាស់ផ្នែកខ្លះនៃនេះដោយសារម៉ាស៊ីនស្វែងរកមិនល្អរបស់ Microsoft ហើយខ្លះទៀតដោយសារ SEO ក្រោមស្តង់ដារ។
  
  * ការដំឡើង Terraform ត្រូវបានចងក្រងឯកសារយ៉ាងល្អ ហើយដំណើរការ។ ទោះយ៉ាងណា ការគាំទ្រ Terraform ខ្សោយធៀបនឹង AWS ព្រោះ Microsoft កំពុងកសាងទំនាក់ទំនងអាជីវកម្មជាមួយអ្នកលក់ ដើម្បីធ្វើឧទាហរណ៍ការដំឡើង Terraform តាមខ្សែសង្វាក់។

បទពិសោធន៍របស់មិត្តភក្តិ៖

  * បន្ទាប់ពីយើងបានធ្វើការវាយតម្លៃដោយខ្វាក់របស់យើងផ្ទាល់ យើងបានស្វែងរកបទពិសោធន៍របស់មិត្តភក្តិ។ អ្វីដែលយើងរកឃើញបានបញ្ជាក់បទពិសោធន៍របស់យើង។

  * មិត្តភក្តិបានរាយការណ៍បញ្ហាបន្ថែមអំពីពេលវេលា build និងបញ្ហាជាមួយម៉ាស៊ីនមេ build ដែលនាំយកមកផ្ទាល់។ បញ្ហាទាំងនេះធ្ងន់ធ្ងរជាងបញ្ហា UI យ៉ាងច្រើន ព្រោះការ build គឺជាគោលបំណងស្នូលនៃបំពង់ build ហើយយើងរំពឹងថានឹងធ្វើវាច្រើនដងក្នុងមួយថ្ងៃ។

  * យើងបានរកឃើញការចូលរួមដ៏ឆ្នើមពីមិត្តរួមក្រុម Azure នៅក្នុងតំបន់ពិភាក្សា។ សូមសរសើរ Microsoft ចំពោះរឿងនេះ។ យើងចាប់អារម្មណ៍ជាពិសេសចំពោះ Edward Thomson ដែលជា Azure PM និងអ្នកសរសេរកូដ ដោយសារការចូលរួម ភាពត្រង់ និងការពន្យល់បច្ចេកទេសរបស់គាត់។


### ផលវិបាក

ការជ្រើសរើស Microsoft Azure DevOps មើលទៅទំនងជាថ្លៃជាង (~3 ដង) ទាំងពេលវេលា និងថ្លៃដើម ជាងការមិនជ្រើស Azure។


## ពាក់ព័ន្ធ


### ការសម្រេចចិត្តពាក់ព័ន្ធ

ប្រសិនបើយើងជ្រើស Azure DevOps មានផលិតផលពាក់ព័ន្ធជាច្រើន រួមមាន Azure Repo, Azure Pipeline ។ល។ យើងជឿថាប្រសិនបើយើងជ្រើស Azure Devops នេះអាចធ្វើឱ្យងាយស្រួលជាងក្នុងការប្រើសមត្ថភាព Azure បន្ថែម ឬអាចធ្វើឱ្យពិបាកជាងក្នុងការប្រើសមត្ថភាពរបស់អ្នកលក់ផ្សេងទៀត។

យើងជឿថា Microsoft កំពុងមានវឌ្ឍនភាពធំក្នុងបទពិសោធន៍អ្នកអភិវឌ្ឍន៍ ហើយយើងឃើញ Microsoft ធ្វើការទិញយកឧបករណ៍អ្នកអភិវឌ្ឍន៍ដ៏ធំ (ឧ. GitHub) និងភាពអាស្រ័យ (ឧ. Citus)។

ប្រសិនបើយើងជ្រើស Azure DevOps នោះយើងអាចចង់សង្កត់ធ្ងន់លើការជ្រើសរើសផលិតផលដែលទិញយកដោយ Microsoft ហើយយើងក៏អាចចង់ចូលទៅរកផលិតផលដែលទិញយកទាំងនោះដោយប្រុងប្រយ័ត្ន/ការវាយតម្លៃច្រើនជាង ដោយសារការបដិសេធសរីរាង្គដែលអាចកើតមាន ឧ. ហានិភ័យនៃការចាកចេញរបស់បុគ្គលិក។

### Windows Development MVP

ខ្ញុំជា Windows Development MVP។ ខ្ញុំមានអារម្មណ៍ថាខ្ញុំត្រូវទទួលខុសត្រូវខ្លះចំពោះការមិនបានបន្លឺសម្លេងឱ្យខ្លាំងអំពីបញ្ហាទាំងនេះ។ ប៉ុន្តែត្រូវនិយាយថា ខ្ញុំខកចិត្តដែលបានឮថាអ្នក “ភ្ញាក់ផ្អើល” អំពីបញ្ហា UX។ ខ្ញុំបានប្រាប់ក្រុមរបស់អ្នកថា UX គឺអាក្រក់ខ្លាំង (ឧ. តាំងពីមុនពេលចាប់ផ្តើម) ហើយបានឮតបវិញជានិច្ចថា “យើងដឹង យើងកំពុងកែវា”។ ខ្ញុំនឹងចាប់ផ្តើមធ្វើឱ្យមតិកែលម្អមានរូបភាពផ្លូវការ ហើយរុញវាតាមបំពង់ សូមតាមដាន។ ខ្ញុំក៏នៅក្នុងតំបន់ (Bellevue) ដែរ ចង់ចូលមកព្យាយាមដាក់កម្មវិធី oss .net/wpf/uwp ដ៏សាមញ្ញរបស់យើងចូលបំពង់។ ខ្ញុំសង្ស័យថាវានឹងបើកភ្នែកទាំងពីរនាក់យើង។

ឧទាហរណ៍មួយចំនួន៖

* ខ្ញុំរកឃើញថាវាមិនអាចកែ PATH សម្រាប់ឧបករណ៍ផ្ទាល់ខ្លួនមួយចំនួនបានទេ

* បទពិសោធន៍បំពង់ថ្មី (New Pipeline) មិនសមហេតុផលទាល់តែសោះ អ្នកប្រើថ្មីដែលចុចជុំវិញនឹងបញ្ចប់នៅឯឯកសារខុសនៅទីបំផុត។
