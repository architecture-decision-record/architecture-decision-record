# บันทึกการตัดสินใจด้านสถาปัตยกรรม: เฟรมเวิร์ก Ruby on Rails

## บริบท

- องค์กรกำลังพัฒนาเว็บแอปพลิเคชันที่มีตรรกะทางธุรกิจซับซ้อนและมีการเชื่อมต่อหลายรายการกับบริการของบุคคลที่สาม

- ทีมมีประสบการณ์ในการสร้างเว็บแอปพลิเคชันด้วย Ruby on Rails

- ต้องเลือกเฟรมเวิร์กเว็บที่ส่งเสริมการพัฒนาที่รวดเร็ว ความสามารถในการปรับขนาด และความสามารถในการบำรุงรักษา

## การตัดสินใจ

- ใช้ Ruby on Rails เป็นเฟรมเวิร์กสำหรับพัฒนาเว็บแอปพลิเคชัน

## การให้เหตุผล

- Ruby on Rails เป็นเฟรมเวิร์กเว็บที่สมบูรณ์ เสถียร และนำไปใช้อย่างกว้างขวาง ซึ่งพิสูจน์แล้วว่ามีประสิทธิผลในการสร้างเว็บแอปพลิเคชันที่ซับซ้อน

- เฟรมเวิร์กใช้รูปแบบสถาปัตยกรรม Model-View-Controller (MVC) ซึ่งส่งเสริมการแยกความรับผิดชอบและเพิ่มความสามารถในการนำโค้ดกลับมาใช้ซ้ำและบำรุงรักษา

- Rails ให้ฟีเจอร์ในตัวมากมาย เช่น ActiveRecord สำหรับการโต้ตอบกับฐานข้อมูลและ ActionMailer สำหรับการจัดการอีเมล ซึ่งช่วยประหยัดเวลาพัฒนาและทำให้โค้ดเรียบง่ายขึ้น

- เฟรมเวิร์กมีชุมชนที่ใหญ่และคึกคัก มีโมดูลและปลั๊กอินที่ใช้ซ้ำได้มากมายเพื่อเพิ่มฟังก์ชันและแก้ปัญหาทั่วไป

- Ruby on Rails รองรับการพัฒนาแบบขับเคลื่อนด้วยการทดสอบ (TDD) และการพัฒนาแบบขับเคลื่อนด้วยพฤติกรรม (BDD) ซึ่งช่วยให้นักพัฒนาเขียนการทดสอบอัตโนมัติสำหรับโค้ดของตน เพื่อให้แน่ใจว่าทำงานตามที่คาดและลดข้อบกพร่องและการถดถอย

- Ruby เป็นภาษาระดับสูงที่ส่งเสริมผลิตภาพของนักพัฒนาและความอ่านง่ายของโค้ด และทำหน้าที่เป็นภาษากาวที่ทรงพลังสำหรับการเชื่อมต่อกับบริการและ API ของบุคคลที่สามหลากหลาย

## ผลที่ตามมา

- ทีมต้องแน่ใจว่าสถาปัตยกรรมและการออกแบบของเว็บแอปพลิเคชันเป็นไปตามข้อตกลงและแนวปฏิบัติที่ดีที่สุดของ Rails เพื่อให้ได้ประโยชน์จากเฟรมเวิร์กสูงสุด

- นักพัฒนาต้องเข้าใจภาษา Ruby และเฟรมเวิร์ก Rails ได้ดี แม้เอกสารและชุมชนของ Rails จะให้คำแนะนำและการสนับสนุนได้

- อาจมีเส้นโค้งการเรียนรู้สำหรับนักพัฒนาที่ใหม่กับ Ruby และ Rails แม้ประโยชน์ของเฟรมเวิร์กจะทำให้การลงทุนในการฝึกอบรมและการปฐมนิเทศสมเหตุสมผลได้

- ทีมต้องติดตามประสิทธิภาพและความสามารถในการปรับขนาดของแอปพลิเคชัน และอาจต้องปรับแต่งแบบสอบถามฐานข้อมูลและเพิ่มประสิทธิภาพการแคชเพื่อจัดการข้อมูลและทราฟฟิกปริมาณมาก
