## កំណត់ត្រាការសម្រេចចិត្តខាងស្ថាបត្យកម្មគឺជាអ្វី?

**កំណត់ត្រាការសម្រេចចិត្តខាងស្ថាបត្យកម្ម** (ADR) គឺជាឯកសារដែលកត់ត្រាការសម្រេចចិត្តខាងស្ថាបត្យកម្មដ៏សំខាន់មួយ រួមជាមួយបរិបទ និងផលវិបាករបស់វា។

**ការសម្រេចចិត្តខាងស្ថាបត្យកម្ម** (AD) គឺជាជម្រើសក្នុងការរចនាកម្មវិធីដែលឆ្លើយតបនឹងតម្រូវការដ៏សំខាន់មួយ។

**កំណត់ហេតុការសម្រេចចិត្តខាងស្ថាបត្យកម្ម** (ADL) គឺជាបណ្តុំនៃ ADR ទាំងអស់ដែលបានបង្កើត និងថែរក្សាសម្រាប់គម្រោង (ឬអង្គការ) មួយ។

**តម្រូវការដែលមានសារៈសំខាន់ខាងស្ថាបត្យកម្ម** (ASR) គឺជាតម្រូវការដែលមានឥទ្ធិពលអាចវាស់វែងបានលើស្ថាបត្យកម្មរបស់ប្រព័ន្ធកម្មវិធី។

ទាំងអស់នេះស្ថិតក្នុងប្រធានបទ **ការគ្រប់គ្រងចំណេះដឹងខាងស្ថាបត្យកម្ម** (AKM)។

គោលបំណងនៃឯកសារនេះគឺផ្តល់ទិដ្ឋភាពទូទៅយ៉ាងរហ័សអំពី ADR របៀបបង្កើតវា និងកន្លែងដែលអាចរកព័ត៌មានបន្ថែម។

ពាក្យកាត់៖

  * **AD**: ការសម្រេចចិត្តខាងស្ថាបត្យកម្ម

  * **ADL**: កំណត់ហេតុការសម្រេចចិត្តខាងស្ថាបត្យកម្ម

  * **ADR**: កំណត់ត្រាការសម្រេចចិត្តខាងស្ថាបត្យកម្ម

  * **AKM**: ការគ្រប់គ្រងចំណេះដឹងខាងស្ថាបត្យកម្ម

  * **ASR**: តម្រូវការដែលមានសារៈសំខាន់ខាងស្ថាបត្យកម្ម

## របៀបចាប់ផ្តើមប្រើ ADR

ដើម្បីចាប់ផ្តើមប្រើ ADR សូមពិភាក្សាជាមួយមិត្តរួមក្រុមរបស់អ្នកអំពីផ្នែកទាំងនេះ។

ការកំណត់អត្តសញ្ញាណការសម្រេចចិត្ត៖

  * តើ AD មានភាពបន្ទាន់ និងសំខាន់កម្រិតណា?

  * តើវាត្រូវតែធ្វើឡើងឥឡូវនេះ ឬអាចរង់ចាំរហូតដល់ដឹងបន្ថែម?

  * ទាំងបទពិសោធន៍ផ្ទាល់ខ្លួន និងរួម ព្រមទាំងវិធីសាស្ត្រ និងការអនុវត្តរចនាដែលត្រូវបានទទួលស្គាល់ អាចជួយក្នុងការកំណត់អត្តសញ្ញាណការសម្រេចចិត្ត។

  * ជាការល្អ គួររក្សាបញ្ជីកិច្ចការការសម្រេចចិត្តដែលបំពេញបន្ថែមបញ្ជីកិច្ចការផលិតផល។

ការសម្រេចចិត្ត៖

  * មានបច្ចេកទេសសម្រេចចិត្តជាច្រើន ទាំងបច្ចេកទេសទូទៅ និងបច្ចេកទេសជាក់លាក់សម្រាប់ស្ថាបត្យកម្មកម្មវិធី ឧទាហរណ៍ ការគូសផែនទីសន្ទនា។

  * ការសម្រេចចិត្តជាក្រុមគឺជាប្រធានបទស្រាវជ្រាវដែលកំពុងសកម្ម។

ការអនុវត្ត និងការបង្ខំឱ្យអនុវត្តការសម្រេចចិត្ត៖

  * AD ត្រូវបានប្រើក្នុងការរចនាកម្មវិធី ដូច្នេះវាត្រូវតែត្រូវបានប្រាប់ និងទទួលយកដោយភាគីពាក់ព័ន្ធនៃប្រព័ន្ធដែលផ្តល់ថវិកា អភិវឌ្ឍ និងប្រតិបត្តិការវា។

  * រចនាប័ទ្មកូដដែលបង្ហាញស្ថាបត្យកម្មច្បាស់លាស់ និងការពិនិត្យកូដដែលផ្តោតលើកង្វល់ និងការសម្រេចចិត្តខាងស្ថាបត្យកម្ម គឺជាការអនុវត្តពាក់ព័ន្ធពីរ។

  * AD ក៏ត្រូវតែត្រូវបានពិចារណា (ឡើងវិញ) នៅពេលធ្វើទំនើបកម្មប្រព័ន្ធកម្មវិធីក្នុងការវិវត្តកម្មវិធី។

ការចែករំលែកការសម្រេចចិត្ត (ស្រេចចិត្ត)៖

  * AD ជាច្រើនកើតឡើងម្តងទៀតនៅទូទាំងគម្រោង។

  * ដូច្នេះ បទពិសោធន៍ជាមួយការសម្រេចចិត្តពីមុន ទាំងល្អ និងអាក្រក់ អាចជាទ្រព្យសម្បត្តិប្រើឡើងវិញដ៏មានតម្លៃ នៅពេលប្រើយុទ្ធសាស្ត្រគ្រប់គ្រងចំណេះដឹងច្បាស់លាស់។

ការចងក្រងឯកសារការសម្រេចចិត្ត៖

  * មានពុម្ព និងឧបករណ៍ជាច្រើនសម្រាប់កត់ត្រាការសម្រេចចិត្ត។

  * សូមមើលសហគមន៍ agile ឧទាហរណ៍ ADR របស់ M. Nygard។

  * សូមមើលដំណើរការវិស្វកម្មកម្មវិធី និងរចនាស្ថាបត្យកម្មបែបប្រពៃណី ឧទាហរណ៍ ប្លង់តារាងដែលស្នើដោយ IBM UMF និងដោយ Tyree និង Akerman ពី CapitalOne។

  * ជំហានខាងលើត្រូវបានយកមកពីអត្ថបទ Wikipedia អំពី [ការសម្រេចចិត្តខាងស្ថាបត្យកម្ម](https://en.wikipedia.org/wiki/Architectural_decision)

## ការណែនាំសម្រាប់សរសេរ ADR ឲ្យបានល្អ

លក្ខណៈនៃ ADR ដែលល្អ៖

* មូលហេតុ៖ ពន្យល់ពីហេតុផលនៃការធ្វើ AD ជាក់លាក់នោះ។ នេះអាចរួមមានបរិបទ (សូមមើលខាងក្រោម) គុណសម្បត្តិ និងគុណវិបត្តិនៃជម្រើសដែលអាចមានផ្សេងៗ ការប្រៀបធៀបមុខងារ ការពិភាក្សាអំពីថ្លៃដើម/អត្ថប្រយោជន៍ និងច្រើនទៀត។

* ជាក់លាក់៖ ADR នីមួយៗគួរនិយាយអំពី AD មួយ មិនមែនច្រើន AD ទេ។

* ត្រាពេលវេលា៖ កំណត់ថាធាតុនីមួយៗក្នុង ADR ត្រូវបានសរសេរនៅពេលណា។ នេះសំខាន់ជាពិសេសសម្រាប់ទិដ្ឋភាពដែលអាចផ្លាស់ប្តូរតាមពេលវេលា ដូចជាថ្លៃដើម កាលវិភាគ ការពង្រីកទំហំ និងអ្វីៗស្រដៀងគ្នា។

* មិនអាចផ្លាស់ប្តូរបាន៖ កុំកែប្រែព័ត៌មានដែលមានស្រាប់ក្នុង ADR។ ផ្ទុយទៅវិញ សូមធ្វើវិសោធនកម្ម ADR ដោយបន្ថែមព័ត៌មានថ្មី ឬជំនួស ADR ដោយបង្កើត ADR ថ្មី។

លក្ខណៈនៃផ្នែក “បរិបទ” ដែលល្អក្នុង ADR៖

* ពន្យល់ពីស្ថានភាពរបស់អង្គការអ្នក និងអាទិភាពអាជីវកម្ម។

* រួមបញ្ចូលមូលហេតុ និងការពិចារណាដោយផ្អែកលើសមាសភាពសង្គម និងជំនាញនៃក្រុមរបស់អ្នក។

* រួមបញ្ចូលព័ត៌មានអំពី ADR បន្តបន្ទាប់ណាមួយ។ វាជារឿងសាមញ្ញដែល ADR មួយបង្កើតតម្រូវការ ADR ច្រើនទៀត ដូចជានៅពេល ADR មួយធ្វើជម្រើសធំគ្របដណ្តប់ ដែលបន្ទាប់មកបង្កើតតម្រូវការសម្រាប់ការសម្រេចចិត្តតូចៗច្រើនទៀត។

## ដំបូន្មានការងារជាក្រុមសម្រាប់ ADR

ប្រសិនបើអ្នកកំពុងពិចារណាប្រើកំណត់ត្រាការសម្រេចចិត្តជាមួយក្រុមរបស់អ្នក នេះជាដំបូន្មានមួយចំនួនដែលយើងបានរៀនពីការធ្វើការជាមួយក្រុមជាច្រើន។

អ្នកមានឱកាសដឹកនាំមិត្តរួមក្រុមរបស់អ្នក ដោយនិយាយគ្នាអំពី “ហេតុអ្វី” ជាជាងបង្ខំ “អ្វី”។ ឧទាហរណ៍ កំណត់ត្រាការសម្រេចចិត្តគឺជាមធ្យោបាយឱ្យក្រុមគិតឆ្លាតជាងមុន និងទំនាក់ទំនងបានល្អជាងមុន។ កំណត់ត្រាការសម្រេចចិត្តគ្មានតម្លៃទេ ប្រសិនបើវាគ្រាន់តែជាតម្រូវការឯកសារបង្ខំក្រោយពេលហើយ។

ក្រុមមួយចំនួនចូលចិត្តឈ្មោះ “ការសម្រេចចិត្ត” ជាងអក្សរកាត់ “ADR” ច្រើន។ នៅពេលក្រុមមួយចំនួនប្រើឈ្មោះថត “decisions” វាដូចជាអំពូលភ្លើងបើក ហើយក្រុមចាប់ផ្តើមដាក់ព័ត៌មានបន្ថែមទៀតក្នុងថតនោះ ដូចជាការសម្រេចចិត្តអំពីអ្នកលក់ ការសម្រេចចិត្តអំពីផែនការ ការសម្រេចចិត្តអំពីកាលវិភាគ ជាដើម។ ព័ត៌មានគ្រប់ប្រភេទទាំងនេះអាចប្រើពុម្ពដូចគ្នា។ យើងសន្មត់ថាមនុស្សរៀនបានលឿនជាងជាមួយពាក្យ (“ការសម្រេចចិត្ត”) ជាងអក្សរកាត់ (“ADR”) ហើយមនុស្សមានការជំរុញកាន់តែខ្លាំងក្នុងការសរសេរឯកសារដែលកំពុងដំណើរការ នៅពេលដកពាក្យ “កំណត់ត្រា” ចេញ ហើយអ្នកអភិវឌ្ឍន៍ និងអ្នកគ្រប់គ្រងមួយចំនួនក៏មិនចូលចិត្តពាក្យ “ស្ថាបត្យកម្ម” ដែរ។

តាមទ្រឹស្តី ភាពមិនអាចផ្លាស់ប្តូរបានគឺល្អបំផុត។ ក្នុងការអនុវត្ត ភាពអាចផ្លាស់ប្តូរបានដំណើរការបានល្អជាងសម្រាប់ក្រុមរបស់យើង។ យើងបញ្ចូលព័ត៌មានថ្មីទៅក្នុង ADR ដែលមានស្រាប់ ជាមួយត្រាកាលបរិច្ឆេទ និងកំណត់ចំណាំថាព័ត៌មាននោះមកដល់បន្ទាប់ពីការសម្រេចចិត្ត។ វិធីសាស្ត្របែបនេះនាំទៅរក “ឯកសាររស់” ដែលយើងទាំងអស់គ្នាអាចធ្វើបច្ចុប្បន្នភាព។ ការធ្វើបច្ចុប្បន្នភាពធម្មតាគឺនៅពេលយើងទទួលបានព័ត៌មានដោយសារមិត្តរួមក្រុមថ្មី ឬការផ្តល់ជូនថ្មី ឬលទ្ធផលជាក់ស្តែងនៃការប្រើប្រាស់របស់យើង ឬបន្ទាប់ពីការផ្លាស់ប្តូរពីភាគីទីបីក្រោយពេលហើយ ដូចជាសមត្ថភាពរបស់អ្នកលក់ ផែនការតម្លៃ កិច្ចព្រមព្រៀងអាជ្ញាប័ណ្ណ ជាដើម។

#### តើអ្នកណាអាចបង្កើត ADR បាន?

ពិចារណាផ្នែកដូចជាបុគ្គលជាក់លាក់ តួនាទីជាក់លាក់ ក្រុមជាក់លាក់ ឬនាយកដ្ឋានជាក់លាក់។ ព្រមទាំងពិចារណាថាតើមានបុគ្គល តួនាទី ក្រុម ឬនាយកដ្ឋានណាដែលអាចបញ្ជាឱ្យបង្កើត ADR ដែរឬទេ មានន័យថាពួកគេស្នើសុំ ADR មួយដែលអ្នកផ្សេងនឹងនិពន្ធ។

ឧទាហរណ៍ចម្លើយ៖ បុគ្គលណាក៏ដោយក្នុងអង្គការរបស់យើងដែលបានអានទំព័រ README នៃកំណត់ត្រាការសម្រេចចិត្តខាងស្ថាបត្យកម្ម អាចស្នើ ADR បាន មានន័យថាបុគ្គលនោះអាចចាប់ផ្តើមសរសេរវា ហើយចែករំលែកជាមួយក្រុម។

ពិចារណាផ្នែកដូចជាវិធីធ្វើការរបស់ក្រុមក្នុងអង្គការរបស់អ្នក រចនាសម្ព័ន្ធប្រព័ន្ធកម្មវិធីរបស់អ្នក ការសម្របសម្រួលរវាងក្រុម ភាពអាចថែទាំបានរយៈពេលវែង ចំណុចប្រទាក់ខាងក្រៅ អ្នកដែលអ្នកចង់ឱ្យទទួលបានអត្ថប្រយោជន៍ និងអ្វីៗស្រដៀងគ្នា។

ឧទាហរណ៍ចម្លើយ៖ យើងចង់បង្កើត ADR នៅពេលយើងចង់ឱ្យអ្នកអភិវឌ្ឍន៍នាពេលអនាគតយល់ពី “ហេតុអ្វី” នៃអ្វីដែលយើងកំពុងធ្វើ។

ពិចារណាផ្នែកដូចជាការសម្រេចចិត្តដែលមិនទាក់ទងនឹងស្ថាបត្យកម្ម ឬតូចតាចដូចជាហានិភ័យតិចតួចបំផុត ឬឯករាជ្យ ឬអ្នកអភិវឌ្ឍន៍តែម្នាក់ ឬត្រូវបានគ្របដណ្តប់ពេញលេញនៅកន្លែងផ្សេងរួចហើយ ដូចជាដោយស្តង់ដារ គោលនយោបាយ ឬឯកសារ ឬបណ្តោះអាសន្ន ដូចជាដំណោះស្រាយបណ្តោះអាសន្ន ភស្តុតាងនៃគំនិត ឬការពិសោធន៍។

ឧទាហរណ៍ចម្លើយ៖ យើងចង់រំលង ADR នៅពេលការសម្រេចចិត្តមានដែនកំណត់ក្នុងវិសាលភាព ពេលវេលា ហានិភ័យ និងថ្លៃដើម ឬត្រូវបានគ្របដណ្តប់នៅកន្លែងផ្សេងរួចហើយ។

#### តើវដ្តជីវិតរបស់ ADR ជាអ្វី?

ពិចារណាផ្នែកដូចជាដំណើរការបង្កើត ដំណើរការស្រាវជ្រាវ ដំណើរការសម្រេចចិត្ត ដំណើរការអនុវត្ត និងដំណើរការបញ្ចប់។ ពិចារណាអំពីរបៀបតាមដានវដ្តជីវិត ADR តាមពេលវេលា ដូចជារបៀបផ្លាស់ប្តូរ ADR ពីស្ថានភាពមួយទៅស្ថានភាពបន្ទាប់ និងរបៀបប្រាប់ភាគីពាក់ព័ន្ធអំពីរឿងនេះ។

ឧទាហរណ៍ចម្លើយ៖ យើងចង់ឱ្យ ADR មានដំណាក់កាលវដ្តជីវិតប្រាំ៖ ចាប់ផ្តើម → ស្រាវជ្រាវ → វាយតម្លៃ → អនុវត្ត → ថែទាំ → បញ្ចប់។

#### តើអ្វីជាលក្ខណៈវិនិច្ឆ័យសម្រាប់ជំហានវដ្តជីវិតរបស់ ADR?

ពិចារណាផ្នែកដូចជាលក្ខណៈវិនិច្ឆ័យទទួលយកសម្រាប់ ADR មានន័យថាតើអ្នកដឹងដោយរបៀបណាថាវាល្អគ្រប់គ្រាន់ដើម្បីរីកចម្រើនពីជំហានវដ្តជីវិតមួយទៅជំហានបន្ទាប់? តើបញ្ហាត្រូវបានបញ្ជាក់ច្បាស់លាស់ឬទេ? តើជម្រើសផ្សេងៗត្រូវបានពិចារណាឬនៅ? តើការដោះដូរត្រូវបានយល់ និងចងក្រងឯកសារបានល្អគ្រប់គ្រាន់ឬទេ?
តើបរិបទពាក់ព័ន្ធទាំងអស់ត្រូវបានរៀបចំរួចរាល់ឬនៅ? តើភាគីពាក់ព័ន្ធទាំងអស់ត្រូវបានចូលរួមឬទេ? តើមតិកែលម្អទាំងអស់ត្រូវបានបញ្ចូលឬនៅ?

ឧទាហរណ៍ចម្លើយ៖ យើងចង់ឱ្យភាគីពាក់ព័ន្ធបោះឆ្នោតលើ ADR នៅពេលក្រុមសកម្ម 1) បានបញ្ចប់ការស្រាវជ្រាវរបស់ខ្លួន 2) បានបញ្ចប់ការវាយតម្លៃរបស់ខ្លួន 3) បានផ្សព្វផ្សាយសំណើ ADR ទៅភាគីពាក់ព័ន្ធ ជាមួយសំណើសុំមតិយោបល់ និងកំណត់ពេលមួយសប្តាហ៍ 4) មតិយោបល់របស់ភាគីពាក់ព័ន្ធទាំងអស់ត្រូវបានបញ្ចូល និងដោះស្រាយ។

#### តើតួនាទី និងទំនួលខុសត្រូវអ្វីខ្លះទាក់ទងនឹង ADR?

ពិចារណាតួនាទីដូចជាអ្នកស្នើ អ្នកស្រាវជ្រាវ អ្នកវាយតម្លៃ អ្នកពិនិត្យ អ្នកអនុម័ត អ្នកថែទាំ និងអ្វីៗស្រដៀងគ្នា។ ពិចារណាទំនួលខុសត្រូវដូចជាការទំនាក់ទំនងជាមួយភាគីពាក់ព័ន្ធ ការធានាថាការរំពឹងទុកត្រូវបានបំពេញ ការចែករំលែកនៅលើគេហទំព័រ ឬអ៊ីនត្រាណែត និងការពិនិត្យការងារជាប្រចាំ ជាពិសេសនៅពេលមានការផ្លាស់ប្តូរពាក់ព័ន្ធ។

ឧទាហរណ៍ចម្លើយ៖ យើងចង់ឱ្យ ADR នីមួយៗមានអ្នកទំនាក់ទំនងចម្បង អ្នកទំនាក់ទំនងបន្ទាប់បន្សំ និងក្រុមទទួលខុសត្រូវជានិច្ច។ ទាំងនេះទទួលខុសត្រូវចំពោះការទំនាក់ទំនង ការផ្សព្វផ្សាយ ការថែទាំ ការពិនិត្យតាមកាលកំណត់យ៉ាងតិចម្តងក្នុងមួយឆ្នាំ និងការបញ្ចប់នៅទីបំផុតតាមការចាំបាច់។

#### តើអភិបាលកិច្ចទាក់ទងនឹង ADR យ៉ាងដូចម្តេច?

ពិចារណាផ្នែកដូចជាវិធីធ្វើការរបស់អង្គការអ្នក តម្រូវការអនុលោមពិសេសណាមួយ ដូចជាទិដ្ឋភាពច្បាប់ ឬទិដ្ឋភាពធនធានមនុស្ស របៀបដែលអ្នកចង់គ្រប់គ្រងឯកភាពទល់នឹងជម្លោះ ទល់នឹងការបញ្ជូនបន្តទៅថ្នាក់លើ។ តើមានផ្នែក បុគ្គល ឬក្រុមណាដែលអាចមានឥទ្ធិពលលើសអ្នកដទៃទាក់ទងនឹង ADR ដូចជាអាចអនុម័តវា បោះឆ្នោតលើវា ឬបដិសេធវា ដែរឬទេ?

ឧទាហរណ៍ចម្លើយ៖ អភិបាលកិច្ចនៃ ADR មានលំដាប់អាទិភាពដូចតទៅ៖ នាយកប្រតិបត្តិ នាយកបច្ចេកវិទ្យា នាយកច្បាប់ ក្រុមដែលអនុវត្ត ADR អ្នកជំនាញក្នុងក្រុមដែលចេះដឹងច្រើនបំផុតអំពី AD។ គ្មានអ្នកណាផ្សេងមានអភិបាលកិច្ចទេ លុះត្រាតែបានពិពណ៌នាក្នុង ADR។

#### តើគោលការណ៍អ្វីខ្លះទាក់ទងនឹង ADR?

ពិចារណាផ្នែកដូចជាវិធីធ្វើការរបស់អង្គការអ្នក ដែលរួមមានការធ្វើចលនាលឿនទល់នឹងយឺត សម្រាប់ឯកភាពក្នុងការសម្រេចចិត្តទល់នឹងជម្លោះក្នុងការសម្រេចចិត្ត សម្រាប់ចំណូលចិត្តហានិភ័យទល់នឹងចំណូលចិត្តសុវត្ថិភាព ការពិភាក្សាជាសាធារណៈទល់នឹងការពិភាក្សាឯកជន និងអ្វីៗស្រដៀងគ្នា។

ឧទាហរណ៍ចម្លើយ៖ យើងប្រើគោលការណ៍ភាពជាអ្នកដឹកនាំនៃការលំអៀងទៅរកសកម្មភាព មិនយល់ស្របហើយប្តេជ្ញា ការប៉ាន់ស្មាន 70% គឺល្អគ្រប់គ្រាន់សម្រាប់ការសម្រេចចិត្តដែលអាចត្រឡប់វិញបានងាយ និងអាចញែកដាច់បានងាយ និងវិធីធ្វើការជាសាធារណៈ លើកលែងតែព័ត៌មានសម្ងាត់ដូចដែលបានពិពណ៌នាក្នុងកិច្ចព្រមព្រៀងការរក្សាការសម្ងាត់របស់អង្គការយើង។

### អ្វីដែលបង្ហាញថាសមហេតុផលក្នុងការមិនបង្កើត ADR?

ពិចារណាផ្នែកដូចជាដំណើរការបង្កើត ដំណើរការស្រាវជ្រាវ ដំណើរការសម្រេចចិត្ត ដំណើរការអនុវត្ត និងដំណើរការបញ្ចប់។ ពិចារណាអំពីរបៀបតាមដានវដ្តជីវិត ADR តាមពេលវេលា ដូចជារបៀបផ្លាស់ប្តូរ ADR ពីស្ថានភាពមួយទៅស្ថានភាពបន្ទាប់ និងរបៀបប្រាប់ភាគីពាក់ព័ន្ធអំពីរឿងនេះ។

ឧទាហរណ៍ចម្លើយ៖ យើងចង់ឱ្យ ADR មានដំណាក់កាលវដ្តជីវិតប្រាំ៖ ចាប់ផ្តើម → ស្រាវជ្រាវ → វាយតម្លៃ → អនុវត្ត → ថែទាំ → បញ្ចប់។

### តើអ្វីជាលក្ខណៈវិនិច្ឆ័យសម្រាប់ជំហានវដ្តជីវិតរបស់ ADR?

តើបរិបទពាក់ព័ន្ធទាំងអស់ត្រូវបានរៀបចំរួចរាល់ឬនៅ? តើភាគីពាក់ព័ន្ធទាំងអស់ត្រូវបានចូលរួមឬទេ? តើមតិកែលម្អទាំងអស់ត្រូវបានបញ្ចូលឬនៅ?

### តើតួនាទី និងទំនួលខុសត្រូវអ្វីខ្លះទាក់ទងនឹង ADR?

### តើអភិបាលកិច្ចទាក់ទងនឹង ADR យ៉ាងដូចម្តេច?

- ដ្យាក្រាមដាក់ពង្រាយ (Deployment Diagram) បង្ហាញផ្នែករឹង/កុំព្យូទ័ររូបវន្តដែលសមាសភាគកម្មវិធីត្រូវបានដាក់ពង្រាយទៅ។

- ដ្យាក្រាមសកម្មភាព (Activity Diagram) បង្ហាញលំហូរការងារនៃសកម្មភាពដែលប្រព័ន្ធកម្មវិធីអនុវត្ត ដូចជា AI របស់ NPC។

ការសម្រេចចិត្តអំពីការអនុលោម ការសម្រេចចិត្តព្យាបាល និងវេជ្ជសាស្ត្រ ការសម្រេចចិត្តអំពីសុវត្ថិភាព
និងច្រើនទៀត។

ដំណើរការជាមួយប្រព័ន្ធ CI ណាមួយ (GitLab, Jenkins, CircleCI) និងជា pre-commit hook។
កូដចំហ។ អាជ្ញាប័ណ្ណ MIT។

[ADR Guard](https://github.com/chohan-sarmad-ali/delivery-gates) គឺជា GitHub
Action ដែលធ្វើឱ្យ pull request បរាជ័យ នៅពេលផ្លូវកូដដែលត្រូវបានតាមដានផ្លាស់ប្តូរ ដោយគ្មាន
កំណត់ត្រាការសម្រេចចិត្តខាងស្ថាបត្យកម្មត្រូវបានបន្ថែម ឬធ្វើបច្ចុប្បន្នភាព។ ការលើកលែងគឺច្បាស់លាស់៖ បន្ទាត់
`ADR-Exempt:` ជាមួយហេតុផលនឹងឆ្លងកាត់ផ្លូវទ្វារ ហើយត្រូវបានសរសេរចូលក្នុងសេចក្តីសង្ខេប
