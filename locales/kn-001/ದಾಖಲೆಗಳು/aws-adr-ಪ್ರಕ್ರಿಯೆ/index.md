# AWS ವಾಸ್ತುಶಿಲ್ಪ ನಿರ್ಧಾರ ದಾಖಲೆ ಪ್ರಕ್ರಿಯೆ

https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html

ವಾಸ್ತುಶಿಲ್ಪ ನಿರ್ಧಾರ ದಾಖಲೆ (ADR) ಎಂದರೆ ತಂಡವು ತಾನು ನಿರ್ಮಿಸಲು ಯೋಜಿಸುತ್ತಿರುವ ತಂತ್ರಾಂಶ ವಾಸ್ತುಶಿಲ್ಪದ ಒಂದು ಮಹತ್ವದ ಅಂಶದ ಬಗ್ಗೆ ಮಾಡುವ ಆಯ್ಕೆಯನ್ನು ವಿವರಿಸುವ ದಾಖಲೆ. ಪ್ರತಿಯೊಂದು ADR ವಾಸ್ತುಶಿಲ್ಪ ನಿರ್ಧಾರವನ್ನು, ಅದರ ಸಂದರ್ಭವನ್ನು ಮತ್ತು ಅದರ ಪರಿಣಾಮಗಳನ್ನು ವಿವರಿಸುತ್ತದೆ. ADR ಗಳಿಗೆ ಸ್ಥಿತಿಗಳಿರುತ್ತವೆ, ಆದ್ದರಿಂದ ಅವು ಒಂದು ಜೀವನಚಕ್ರವನ್ನು ಅನುಸರಿಸುತ್ತವೆ. ADR ನ ಉದಾಹರಣೆಗಾಗಿ ಅನುಬಂಧವನ್ನು ನೋಡಿ.

ADR ಪ್ರಕ್ರಿಯೆಯು ವಾಸ್ತುಶಿಲ್ಪ ನಿರ್ಧಾರ ದಾಖಲೆಗಳ ಸಂಗ್ರಹವನ್ನು ಉತ್ಪಾದಿಸುತ್ತದೆ. ಈ ಸಂಗ್ರಹವು ನಿರ್ಧಾರ ಲಾಗ್ ಅನ್ನು ರೂಪಿಸುತ್ತದೆ. ನಿರ್ಧಾರ ಲಾಗ್ ಯೋಜನೆಯ ಸಂದರ್ಭವನ್ನೂ, ವಿವರವಾದ ಅನುಷ್ಠಾನ ಮತ್ತು ವಿನ್ಯಾಸ ಮಾಹಿತಿಯನ್ನೂ ಒದಗಿಸುತ್ತದೆ. ಯೋಜನೆಯ ಸದಸ್ಯರು ಯೋಜನೆಯ ಸಂದರ್ಭದ ಸಮಗ್ರ ನೋಟ ಪಡೆಯಲು ಪ್ರತಿ ADR ನ ಶೀರ್ಷಿಕೆಗಳನ್ನು ಸ್ಥೂಲವಾಗಿ ಓದುತ್ತಾರೆ. ಯೋಜನೆಯ ಅನುಷ್ಠಾನ ಮತ್ತು ವಿನ್ಯಾಸ ಆಯ್ಕೆಗಳನ್ನು ಆಳವಾಗಿ ತಿಳಿಯಲು ಅವರು ADR ಗಳನ್ನು ಓದುತ್ತಾರೆ.

ತಂಡವು ADR ಅನ್ನು ಸ್ವೀಕರಿಸಿದ ಮೇಲೆ ಅದು ಬದಲಾಯಿಸಲಾಗದ್ದಾಗುತ್ತದೆ. ಹೊಸ ಒಳನೋಟಗಳಿಂದಾಗಿ ಬೇರೆ ನಿರ್ಧಾರ ಅಗತ್ಯವಾದರೆ, ತಂಡವು ಹೊಸ ADR ಅನ್ನು ಪ್ರಸ್ತಾಪಿಸುತ್ತದೆ. ತಂಡವು ಹೊಸ ADR ಅನ್ನು ಸ್ವೀಕರಿಸಿದಾಗ ಅದು ಹಿಂದಿನ ADR ಅನ್ನು ಅತಿಕ್ರಮಿಸುತ್ತದೆ.

## ADR ಪ್ರಕ್ರಿಯೆಯ ವ್ಯಾಪ್ತಿ

ತಂತ್ರಾಂಶ ಯೋಜನೆ ಅಥವಾ ಉತ್ಪನ್ನದ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವ, ವಾಸ್ತುಶಿಲ್ಪದ ದೃಷ್ಟಿಯಿಂದ ಮಹತ್ವದ ಪ್ರತಿಯೊಂದು ನಿರ್ಧಾರಕ್ಕೂ ಯೋಜನೆಯ ಸದಸ್ಯರು ADR ರಚಿಸಬೇಕು. ಇವುಗಳಲ್ಲಿ ಈ ಕೆಳಗಿನವು ಸೇರಿವೆ (Richards and Ford 2020):

* ರಚನೆ (ಉದಾಹರಣೆಗೆ, ಮೈಕ್ರೋಸರ್ವಿಸ್‌ಗಳಂತಹ ಮಾದರಿಗಳು)

* ಕಾರ್ಯಾತ್ಮಕವಲ್ಲದ ಅವಶ್ಯಕತೆಗಳು (ಭದ್ರತೆ, ಹೆಚ್ಚಿನ ಲಭ್ಯತೆ ಮತ್ತು ದೋಷ ಸಹಿಷ್ಣುತೆ)

* ಅವಲಂಬನೆಗಳು (ಘಟಕಗಳ ಜೋಡಣೆ)

* ಇಂಟರ್ಫೇಸ್‌ಗಳು (API ಗಳು ಮತ್ತು ಪ್ರಕಟಿತ ಒಪ್ಪಂದಗಳು)

* ನಿರ್ಮಾಣ ತಂತ್ರಗಳು (ಗ್ರಂಥಾಲಯಗಳು, ಚೌಕಟ್ಟುಗಳು, ಸಾಧನಗಳು ಮತ್ತು ಪ್ರಕ್ರಿಯೆಗಳು)

* ಕಾರ್ಯಾತ್ಮಕ ಮತ್ತು ಕಾರ್ಯಾತ್ಮಕವಲ್ಲದ ಅವಶ್ಯಕತೆಗಳು ADR ಪ್ರಕ್ರಿಯೆಗೆ ಅತ್ಯಂತ ಸಾಮಾನ್ಯ ಇನ್‌ಪುಟ್‌ಗಳಾಗಿವೆ.


## ADR ವಿಷಯಗಳು

ತಂಡವು ADR ನ ಅಗತ್ಯವನ್ನು ಗುರುತಿಸಿದಾಗ, ತಂಡದ ಒಬ್ಬ ಸದಸ್ಯರು ಯೋಜನೆಯಾದ್ಯಂತದ ಟೆಂಪ್ಲೇಟಿನ ಆಧಾರದ ಮೇಲೆ ADR ಬರೆಯಲು ಪ್ರಾರಂಭಿಸುತ್ತಾರೆ. (ಉದಾಹರಣೆ ಟೆಂಪ್ಲೇಟುಗಳಿಗಾಗಿ ADR GitHub ಸಂಸ್ಥೆಯನ್ನು ನೋಡಿ.) ಟೆಂಪ್ಲೇಟು ADR ರಚನೆಯನ್ನು ಸರಳಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ADR ಎಲ್ಲಾ ಸಂಬಂಧಿತ ಮಾಹಿತಿಯನ್ನು ಸೆರೆಹಿಡಿಯುವುದನ್ನು ಖಚಿತಪಡಿಸುತ್ತದೆ. ಕನಿಷ್ಠ ಪಕ್ಷ, ಪ್ರತಿ ADR ನಿರ್ಧಾರದ ಸಂದರ್ಭವನ್ನು, ನಿರ್ಧಾರವನ್ನೇ, ಮತ್ತು ಯೋಜನೆ ಹಾಗೂ ಅದರ ಫಲಿತಾಂಶಗಳ ಮೇಲೆ ನಿರ್ಧಾರದ ಪರಿಣಾಮಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸಬೇಕು. (ಈ ವಿಭಾಗಗಳ ಉದಾಹರಣೆಗಳಿಗಾಗಿ ಅನುಬಂಧವನ್ನು ನೋಡಿ.) ADR ರಚನೆಯ ಅತ್ಯಂತ ಶಕ್ತಿಯುತ ಅಂಶಗಳಲ್ಲಿ ಒಂದೆಂದರೆ, ತಂಡವು ಅದನ್ನು ಹೇಗೆ ಅನುಷ್ಠಾನಗೊಳಿಸಿತು ಎಂಬುದಕ್ಕಿಂತ ನಿರ್ಧಾರದ ಕಾರಣದ ಮೇಲೆ ಅದು ಗಮನ ಕೇಂದ್ರೀಕರಿಸುತ್ತದೆ. ತಂಡವು ಆ ನಿರ್ಧಾರವನ್ನು ಏಕೆ ಮಾಡಿತು ಎಂಬುದನ್ನು ಅರ್ಥಮಾಡಿಕೊಳ್ಳುವುದರಿಂದ ಇತರ ತಂಡದ ಸದಸ್ಯರು ಆ ನಿರ್ಧಾರವನ್ನು ಒಪ್ಪಿಕೊಳ್ಳುವುದು ಸುಲಭವಾಗುತ್ತದೆ, ಮತ್ತು ನಿರ್ಧಾರ ತೆಗೆದುಕೊಳ್ಳುವ ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿ ಭಾಗಿಯಾಗದ ಇತರ ವಾಸ್ತುಶಿಲ್ಪಿಗಳು ಭವಿಷ್ಯದಲ್ಲಿ ಆ ನಿರ್ಧಾರವನ್ನು ತಳ್ಳಿಹಾಕುವುದನ್ನು ತಡೆಯುತ್ತದೆ.


## ADR ಸ್ವೀಕಾರ ಪ್ರಕ್ರಿಯೆ

ತಂಡದ ಪ್ರತಿಯೊಬ್ಬ ಸದಸ್ಯರೂ ADR ರಚಿಸಬಹುದು, ಆದರೆ ತಂಡವು ADR ನ ಮಾಲೀಕತ್ವದ ವ್ಯಾಖ್ಯಾನವನ್ನು ಸ್ಥಾಪಿಸಬೇಕು. ADR ನ ಮಾಲೀಕರಾದ ಪ್ರತಿ ಲೇಖಕರು ADR ವಿಷಯವನ್ನು ಸಕ್ರಿಯವಾಗಿ ನಿರ್ವಹಿಸಬೇಕು ಮತ್ತು ತಿಳಿಸಬೇಕು. ಈ ಮಾಲೀಕತ್ವವನ್ನು ಸ್ಪಷ್ಟಪಡಿಸಲು, ಈ ಮಾರ್ಗದರ್ಶಿ ಮುಂದಿನ ವಿಭಾಗಗಳಲ್ಲಿ ADR ಲೇಖಕರನ್ನು ADR ಮಾಲೀಕರು ಎಂದು ಉಲ್ಲೇಖಿಸುತ್ತದೆ. ಇತರ ತಂಡದ ಸದಸ್ಯರು ಯಾವಾಗಲೂ ADR ಗೆ ಕೊಡುಗೆ ನೀಡಬಹುದು. ತಂಡವು ADR ಅನ್ನು ಸ್ವೀಕರಿಸುವ ಮೊದಲು ಅದರ ವಿಷಯ ಬದಲಾದರೆ, ಮಾಲೀಕರು ಆ ಬದಲಾವಣೆಗಳನ್ನು ಅನುಮೋದಿಸಬೇಕು.

ತಂಡವು ವಾಸ್ತುಶಿಲ್ಪ ನಿರ್ಧಾರವನ್ನು ಮತ್ತು ಅದರ ಮಾಲೀಕರನ್ನು ಗುರುತಿಸಿದ ನಂತರ, ADR ಮಾಲೀಕರು ಪ್ರಕ್ರಿಯೆಯ ಆರಂಭದಲ್ಲಿ ADR ಅನ್ನು **ಪ್ರಸ್ತಾಪಿತ** (Proposed) ಸ್ಥಿತಿಯಲ್ಲಿ ಒದಗಿಸುತ್ತಾರೆ. ಪ್ರಸ್ತಾಪಿತ ಸ್ಥಿತಿಯಲ್ಲಿರುವ ADR ಗಳು ಪರಿಶೀಲನೆಗೆ ಸಿದ್ಧವಾಗಿರುತ್ತವೆ.

ನಂತರ ADR ಮಾಲೀಕರು ADR ಗೆ ಪರಿಶೀಲನೆ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತಾರೆ. ADR ಪರಿಶೀಲನೆ ಪ್ರಕ್ರಿಯೆಯ ಗುರಿ, ತಂಡವು ADR ಅನ್ನು ಸ್ವೀಕರಿಸಬೇಕೇ, ಅದಕ್ಕೆ ಮರುಕೆಲಸ ಬೇಕೆಂದು ನಿರ್ಧರಿಸಬೇಕೇ, ಅಥವಾ ಅದನ್ನು ತಿರಸ್ಕರಿಸಬೇಕೇ ಎಂದು ನಿರ್ಧರಿಸುವುದು. ಮಾಲೀಕರೂ ಸೇರಿದಂತೆ ಯೋಜನಾ ತಂಡವು ADR ಅನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ. ಪರಿಶೀಲನೆ ಸಭೆಯು ADR ಓದಲು ಮೀಸಲಾದ ಸಮಯದಿಂದ ಪ್ರಾರಂಭವಾಗಬೇಕು. ಸರಾಸರಿ 10 ರಿಂದ 15 ನಿಮಿಷ ಸಾಕು. ಈ ಸಮಯದಲ್ಲಿ ಪ್ರತಿ ತಂಡದ ಸದಸ್ಯರು ದಾಖಲೆಯನ್ನು ಓದಿ, ಅಸ್ಪಷ್ಟ ವಿಷಯಗಳನ್ನು ಗುರುತಿಸಲು ಕಾಮೆಂಟ್‌ಗಳನ್ನು ಮತ್ತು ಪ್ರಶ್ನೆಗಳನ್ನು ಸೇರಿಸುತ್ತಾರೆ. ಪರಿಶೀಲನೆ ಹಂತದ ನಂತರ, ADR ಮಾಲೀಕರು ಪ್ರತಿ ಕಾಮೆಂಟ್ ಅನ್ನು ಓದಿ ತಂಡದೊಂದಿಗೆ ಚರ್ಚಿಸುತ್ತಾರೆ.

ADR ಅನ್ನು ಸುಧಾರಿಸಲು ತಂಡವು ಕ್ರಿಯಾ ಅಂಶಗಳನ್ನು ಕಂಡುಕೊಂಡರೆ, ADR ನ ಸ್ಥಿತಿ **ಪ್ರಸ್ತಾಪಿತ** ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ADR ಮಾಲೀಕರು ಕ್ರಿಯೆಗಳನ್ನು ರೂಪಿಸಿ, ತಂಡದ ಸಹಯೋಗದೊಂದಿಗೆ ಪ್ರತಿ ಕ್ರಿಯೆಗೆ ನಿಯೋಜಿತರನ್ನು ಸೇರಿಸುತ್ತಾರೆ. ಪ್ರತಿ ತಂಡದ ಸದಸ್ಯರು ಕ್ರಿಯಾ ಅಂಶಗಳಿಗೆ ಕೊಡುಗೆ ನೀಡಬಹುದು ಮತ್ತು ಅವುಗಳನ್ನು ಪರಿಹರಿಸಬಹುದು. ಪರಿಶೀಲನೆ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಮರುನಿಗದಿಪಡಿಸುವುದು ADR ಮಾಲೀಕರ ಜವಾಬ್ದಾರಿ.

ತಂಡವು ADR ಅನ್ನು ತಿರಸ್ಕರಿಸಲು ಸಹ ನಿರ್ಧರಿಸಬಹುದು. ಈ ಸಂದರ್ಭದಲ್ಲಿ, ಅದೇ ವಿಷಯದ ಬಗ್ಗೆ ಭವಿಷ್ಯದ ಚರ್ಚೆಗಳನ್ನು ತಡೆಯಲು ADR ಮಾಲೀಕರು ತಿರಸ್ಕಾರದ ಕಾರಣವನ್ನು ಸೇರಿಸುತ್ತಾರೆ. ಮಾಲೀಕರು ADR ಸ್ಥಿತಿಯನ್ನು **ತಿರಸ್ಕೃತ** (Rejected) ಎಂದು ಬದಲಾಯಿಸುತ್ತಾರೆ.

ತಂಡವು ADR ಅನ್ನು ಅನುಮೋದಿಸಿದರೆ, ಮಾಲೀಕರು ಸಮಯಮುದ್ರೆ, ಆವೃತ್ತಿ ಮತ್ತು ಪಾಲುದಾರರ ಪಟ್ಟಿಯನ್ನು ಸೇರಿಸುತ್ತಾರೆ. ನಂತರ ಮಾಲೀಕರು ಸ್ಥಿತಿಯನ್ನು **ಸ್ವೀಕೃತ** (Accepted) ಎಂದು ನವೀಕರಿಸುತ್ತಾರೆ.

ADR ಗಳು ಮತ್ತು ಅವು ರೂಪಿಸುವ ನಿರ್ಧಾರ ಲಾಗ್ ತಂಡವು ಮಾಡಿದ ನಿರ್ಧಾರಗಳನ್ನು ಪ್ರತಿನಿಧಿಸುತ್ತವೆ ಮತ್ತು ಎಲ್ಲಾ ನಿರ್ಧಾರಗಳ ಇತಿಹಾಸವನ್ನು ಒದಗಿಸುತ್ತವೆ. ಸಾಧ್ಯವಿರುವೆಡೆ ಕೋಡ್ ಮತ್ತು ವಾಸ್ತುಶಿಲ್ಪ ಪರಿಶೀಲನೆಗಳ ಸಮಯದಲ್ಲಿ ತಂಡವು ADR ಗಳನ್ನು ಉಲ್ಲೇಖವಾಗಿ ಬಳಸುತ್ತದೆ. ಕೋಡ್ ಪರಿಶೀಲನೆ, ವಿನ್ಯಾಸ ಕಾರ್ಯಗಳು ಮತ್ತು ಅನುಷ್ಠಾನ ಕಾರ್ಯಗಳನ್ನು ನಿರ್ವಹಿಸುವುದರ ಜೊತೆಗೆ, ಉತ್ಪನ್ನದ ಕಾರ್ಯತಂತ್ರದ ನಿರ್ಧಾರಗಳಿಗಾಗಿ ತಂಡದ ಸದಸ್ಯರು ADR ಗಳನ್ನು ಸಂಪರ್ಕಿಸಬೇಕು.

ಉತ್ತಮ ಅಭ್ಯಾಸವಾಗಿ, ಪ್ರತಿ ತಂತ್ರಾಂಶ ಬದಲಾವಣೆಯೂ ಸಹೋದ್ಯೋಗಿಗಳ ಪರಿಶೀಲನೆಗೆ ಒಳಗಾಗಬೇಕು ಮತ್ತು ಕನಿಷ್ಠ ಒಂದು ಅನುಮೋದನೆ ಪಡೆಯಬೇಕು. ಕೋಡ್ ಪರಿಶೀಲನೆಯ ಸಮಯದಲ್ಲಿ, ಪರಿಶೀಲಕರು ಒಂದು ಅಥವಾ ಹೆಚ್ಚು ADR ಗಳನ್ನು ಉಲ್ಲಂಘಿಸುವ ಬದಲಾವಣೆಗಳನ್ನು ಕಂಡುಕೊಳ್ಳಬಹುದು. ಈ ಸಂದರ್ಭದಲ್ಲಿ, ಪರಿಶೀಲಕರು ಕೋಡ್ ಬದಲಾವಣೆಯ ಲೇಖಕರನ್ನು ಕೋಡ್ ನವೀಕರಿಸಲು ಕೇಳುತ್ತಾರೆ ಮತ್ತು ADR ಗೆ ಲಿಂಕ್ ಹಂಚಿಕೊಳ್ಳುತ್ತಾರೆ. ಲೇಖಕರು ಕೋಡ್ ಅನ್ನು ನವೀಕರಿಸಿದಾಗ, ಸಹೋದ್ಯೋಗಿ ಪರಿಶೀಲಕರು ಅದನ್ನು ಅನುಮೋದಿಸುತ್ತಾರೆ ಮತ್ತು ಅದು ಮುಖ್ಯ ಕೋಡ್ ಬೇಸ್‌ಗೆ ವಿಲೀನಗೊಳ್ಳುತ್ತದೆ.


## ADR ಪರಿಶೀಲನೆ ಪ್ರಕ್ರಿಯೆ

ತಂಡವು ADR ಗಳನ್ನು ಸ್ವೀಕರಿಸಿದ ಅಥವಾ ತಿರಸ್ಕರಿಸಿದ ನಂತರ ಅವುಗಳನ್ನು ಬದಲಾಯಿಸಲಾಗದ ದಾಖಲೆಗಳೆಂದು ಪರಿಗಣಿಸಬೇಕು. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ADR ಗೆ ಬದಲಾವಣೆ ಮಾಡಲು ಹೊಸ ADR ರಚಿಸುವುದು, ಹೊಸ ADR ಗೆ ಪರಿಶೀಲನೆ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಸ್ಥಾಪಿಸುವುದು ಮತ್ತು ADR ಅನ್ನು ಅನುಮೋದಿಸುವುದು ಅಗತ್ಯ. ತಂಡವು ಹೊಸ ADR ಅನ್ನು ಅನುಮೋದಿಸಿದರೆ, ಮಾಲೀಕರು ಹಳೆಯ ADR ನ ಸ್ಥಿತಿಯನ್ನು **ಅತಿಕ್ರಮಿತ** (Superseded) ಎಂದು ಬದಲಾಯಿಸಬೇಕು.
