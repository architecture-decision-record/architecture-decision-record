## កំណត់ហេតុការផ្លាស់ប្តូរ

រាយការផ្លាស់ប្តូរចំពោះឯកសារ រួមទាំងស្ថានភាព កាលបរិច្ឆេទ និង URL របស់ PR។

ស្ថានភាពគឺមួយក្នុងចំណោម៖ pending, approved, amended, deprecated។

## ករណីប្រើប្រាស់ដែលបានយោង

រាយឯកសារករណីប្រើប្រាស់ / តម្រូវការទាំងអស់ដែលពាក់ព័ន្ធ។

ADR តម្រូវឱ្យមានយ៉ាងតិចមួយករណីប្រើប្រាស់ដែលពាក់ព័ន្ធ និងបានអនុម័ត។

ទម្រង់៖

- \[ឈ្មោះករណីប្រើប្រាស់\]\(URL\)

បន្ថែមការពន្យល់ ប្រសិនបើ ADR មិនបានដោះស្រាយតម្រូវការទាំងអស់នៃករណីប្រើប្រាស់មួយ។


## បរិបទ

ពិពណ៌នា៖

- របៀបដែលការរចនាមានសារៈសំខាន់ខាងស្ថាបត្យកម្ម ដែលសមនឹងមាន ADR (ប្រៀបធៀបនឹង issue និង PR ធម្មតាដើម្បីដោះស្រាយបញ្ហា)

- វិធីសាស្ត្ររចនាកម្រិតខ្ពស់ (ព័ត៌មានលម្អិតបានពិពណ៌នាក្នុងការរចនាដែលបានស្នើខាងក្រោម)


## ការរចនាដែលបានស្នើ

ព័ត៌មានលម្អិតនៃការរចនា (ដោយមិនចូលទៅក្នុងការអនុវត្ត នៅទីណាដែលអាចធ្វើទៅបាន)។

គ្រោង៖

- សេវាកម្ម/ម៉ូឌុលដែលនឹងរងផលប៉ះពាល់ (ផ្លាស់ប្តូរ)

- សេវាកម្ម/ម៉ូឌុលថ្មីដែលត្រូវបន្ថែម

- ផលប៉ះពាល់លើម៉ូដែល និង DTO (ការផ្លាស់ប្តូរ/ការបន្ថែម/ការលុបចេញ)

- ផលប៉ះពាល់លើ API (ការផ្លាស់ប្តូរ/ការបន្ថែម/ការលុបចេញ)

- ផលប៉ះពាល់លើការកំណត់រចនាសម្ព័ន្ធទូទៅ (ការបង្កើតផ្នែកថ្មី ការផ្លាស់ប្តូរ/ការបន្ថែម/ការលុបចេញ)

- ផលប៉ះពាល់លើ devops


## ការពិចារណា

កត់ត្រាជម្រើសផ្សេង កង្វល់ បញ្ហាបន្ទាប់បន្សំ ឬពាក់ព័ន្ធ និងសំណួរដែលកើតឡើងក្នុងការជជែកវែកញែកអំពី ADR។ 

បញ្ជាក់ថាតើវាត្រូវបានដោះស្រាយ ឬបន្ធូរបន្ថយឬទេ និងដោយរបៀបណា។


## ការសម្រេចចិត្ត

កត់ត្រាព័ត៌មានលម្អិតអំពីការអនុវត្តដ៏សំខាន់ណាមួយដែលបានឯកភាព ការព្រមាន ការពិចារណាអនាគត និងបញ្ហារចនាដែលនៅសល់ ឬពន្យារពេល។

កត់ត្រាផ្នែកណាមួយនៃតម្រូវការដែលមិនត្រូវបានបំពេញដោយការរចនាដែលបានស្នើ។
