## Что такое запись архитектурного решения?

**Запись архитектурного решения** (ADR) — это документ, фиксирующий важное принятое архитектурное решение вместе с его контекстом и последствиями.

**Архитектурное решение** (AD) — это выбор в проектировании программного обеспечения, отвечающий существенному требованию.

**Журнал архитектурных решений** (ADL) — это набор всех ADR, созданных и поддерживаемых для конкретного проекта (или организации).

**Архитектурно значимое требование** (ASR) — это требование, оказывающее измеримое влияние на архитектуру программной системы.

Всё это относится к теме **управления архитектурными знаниями** (AKM).

Цель этого документа — дать быстрый обзор ADR, способов их создания и мест, где искать дополнительную информацию.

Сокращения:

  * **AD**: архитектурное решение

  * **ADL**: журнал архитектурных решений

  * **ADR**: запись архитектурного решения

  * **AKM**: управление архитектурными знаниями

  * **ASR**: архитектурно значимое требование

## Как начать использовать ADR

Чтобы начать использовать ADR, обсудите с коллегами следующие области.

Выявление решений:

  * Насколько срочно и насколько важно AD?

  * Нужно ли принимать его сейчас или можно подождать, пока станет известно больше?

  * Выявлению решений могут помочь как личный и коллективный опыт, так и признанные методы и практики проектирования.

  * В идеале ведите список решений к принятию, дополняющий список дел по продукту.

Принятие решений:

  * Существует ряд техник принятия решений, как общих, так и специфичных для архитектуры программного обеспечения, например картирование диалога.

  * Групповое принятие решений — активная тема исследований.

Реализация и обеспечение соблюдения решений:

  * AD используются при проектировании ПО; следовательно, о них нужно сообщать заинтересованным сторонам системы, которые её финансируют, разрабатывают и эксплуатируют, и они должны их принять.

  * Две родственные практики — архитектурно очевидные стили кодирования и проверки кода, сосредоточенные на архитектурных проблемах и решениях.

  * AD также приходится (пере)рассматривать при модернизации программной системы в ходе эволюции ПО.

Совместное использование решений (необязательно):

  * Многие AD повторяются в разных проектах.

  * Поэтому опыт прошлых решений, как хороший, так и плохой, может быть ценным повторно используемым активом при применении явной стратегии управления знаниями.

Документирование решений:

  * Существует множество шаблонов и инструментов для фиксации решений.

  * Смотрите гибкие сообщества, например ADR М. Найгарда.

  * Смотрите традиционные процессы программной инженерии и проектирования архитектуры, например табличные макеты, предложенные IBM UMF, а также Тайри и Акерманом из CapitalOne.

Подробнее:

  * Приведённые выше шаги взяты из статьи Википедии [Architectural Decision](https://en.wikipedia.org/wiki/Architectural_decision)

## Как начать использовать ADR с инструментами

- [MySpec](https://myspec.dev) — Автоматизированная платформа спецификаций и архитектурных решений, структурирующая устав проекта, техническую архитектуру и ADR в чистый Markdown, доступный через MCP.

Начать использовать ADR с инструментами можно любым удобным способом.

Например:

  * Если вам нравятся Google Drive и онлайн-редактирование, вы можете создать Google Doc или Google Sheet.

  * Если вы любите системы контроля версий исходного кода, например git, вы можете создать файл для каждой ADR.

  * Если вам нравятся инструменты планирования проектов, например Atlassian Jira, вы можете использовать трекер планирования этого инструмента.

  * Если вам нравятся вики, например MediaWiki, вы можете создать вики для ADR.

## Как начать использовать ADR с git

Если вам нравится система контроля версий git, то вот как мы любим начинать использовать ADR с git в типичном программном проекте с исходным кодом.

Создайте каталог для файлов ADR:

```sh
$ mkdir adr
```

Для каждой ADR создайте текстовый файл, например `database.txt`:

```sh
$ vi database.txt
```

Пишите в ADR всё, что хотите. Идеи можно найти в шаблонах этого репозитория.

Закоммитьте ADR в свой git-репозиторий.

## Соглашения об именовании файлов

Если вы решили создавать ADR в обычных текстовых файлах, вам, возможно, стоит выработать собственное соглашение об именовании файлов ADR.

Мы предпочитаем соглашение об именовании файлов, имеющее определённый формат.

Примеры:

  * choose-database.md

  * format-timestamps.md

  * manage-passwords.md

  * handle-exceptions.md

Наше соглашение об именовании файлов:

  * Имя содержит глагольную фразу в повелительном наклонении настоящего времени. Это улучшает читаемость и соответствует формату наших сообщений коммитов.

  * В имени используются строчные буквы и дефисы (как и в этом репозитории). Это баланс между читаемостью и удобством использования в системе.

  * Расширение — markdown. Это может быть полезно для простого форматирования.

## Советы по написанию хороших ADR

Характеристики хорошей ADR:

* Обоснование: объясните причины принятия конкретного AD. Сюда может входить контекст (см. ниже), плюсы и минусы различных возможных вариантов, сравнение функций, обсуждение затрат и выгод и многое другое.

* Конкретность: каждая ADR должна касаться одного AD, а не нескольких.

* Метки времени: указывайте, когда был написан каждый пункт ADR. Это особенно важно для аспектов, которые могут меняться со временем, таких как затраты, графики, масштабирование и т. п.

* Неизменяемость: не изменяйте существующую информацию в ADR. Вместо этого дополняйте ADR, добавляя новую информацию, или заменяйте ADR, создавая новую ADR.

Характеристики хорошего раздела «Контекст» в ADR:

* Объясните ситуацию вашей организации и деловые приоритеты.

* Включите обоснования и соображения, основанные на социальном составе и навыках ваших команд.

* Включите уместные плюсы и минусы и опишите их в терминах, соответствующих вашим потребностям и целям.

Характеристики хорошего раздела «Последствия» в ADR:

* Объясните, что следует из принятия решения. Сюда могут входить эффекты, исходы, результаты, дальнейшие действия и многое другое.

* Включите информацию о любых последующих ADR. Довольно часто одна ADR вызывает потребность в других ADR, например когда одна ADR делает большой всеобъемлющий выбор, который, в свою очередь, порождает потребность в более мелких решениях.

* Включите любые процессы ретроспективного анализа. Обычно команды пересматривают каждую ADR через месяц, чтобы сравнить информацию в ADR с тем, что произошло на практике, чтобы учиться и расти.

Новая ADR может заменить предыдущую ADR:

* Когда принимается AD, заменяющий или делающий недействительной предыдущую ADR, следует создать новую ADR

## Советы по командной работе с ADR

Если вы думаете об использовании записей решений в своей команде, вот несколько советов, которые мы усвоили, работая со многими командами.

У вас есть возможность вести за собой коллег, обсуждая вместе «почему», а не предписывая «что». Например, записи решений — это способ для команд думать умнее и лучше общаться; записи решений не имеют ценности, если это просто навязанное задним числом бумажное требование.

Некоторые команды гораздо больше предпочитают название «решения» (decisions) аббревиатуре «ADR». Когда некоторые команды называют каталог «decisions», будто загорается лампочка, и команда начинает класть в каталог больше информации, например решения о поставщиках, решения по планированию, решения по расписанию и т. д. Для всех таких видов информации можно использовать один и тот же шаблон. Мы предполагаем, что люди быстрее учатся на словах («решения»), чем на аббревиатурах («ADR»), что люди охотнее пишут рабочие документы, когда убрано слово «запись», а также что некоторым разработчикам и некоторым руководителям не нравится слово «архитектура».

В теории неизменяемость идеальна. На практике для наших команд лучше работала изменяемость. Мы вставляем новую информацию в существующую ADR с датой и пометкой о том, что информация появилась после принятия решения. Такой подход приводит к «живому документу», который мы все можем обновлять. Типичные обновления происходят, когда мы получаем информацию благодаря новым коллегам, новым предложениям, реальным результатам нашего использования или изменениям у третьих сторон после принятия решения, например возможностям поставщика, тарифным планам, лицензионным соглашениям и т. д.

## Вопросы о командной работе для ADR

### Кто может создать ADR?

Рассмотрите такие области, как конкретные люди, конкретные роли, конкретные команды или конкретные отделы; также подумайте, есть ли люди, роли, команды или отделы, которые могут заказать ADR, то есть запросить её, а написать её будет кто-то другой. 

Пример ответа: любой сотрудник нашей организации, прочитавший страницу README о записях архитектурных решений, может предложить ADR, то есть может начать её писать и поделиться ею с командой.

### Что оправдывает создание ADR?

Рассмотрите такие области, как способы работы команд вашей организации, структура вашей программной системы, координация между командами, долгосрочная сопровождаемость, внешние интерфейсы, кому вы хотите принести пользу и т. п. 

Пример ответа: мы хотим создавать ADR, когда хотим, чтобы будущие разработчики понимали «почему» того, что мы делаем.

### Что оправдывает отказ от создания ADR?

Рассмотрите такие области, как решения, не связанные с архитектурой, или крошечные, например с минимальным риском, самодостаточные или относящиеся к одному разработчику, либо уже полностью охваченные в другом месте, например стандартами, политиками или документацией, либо временные, например обходные пути, доказательства концепции или эксперименты. 

Пример ответа: мы хотим пропустить ADR, когда решение ограничено по охвату, времени, риску и стоимости или уже охвачено в другом месте.

### Каков жизненный цикл ADR?

Рассмотрите такие области, как процесс создания, процесс исследования, процесс принятия решения, процесс реализации и процесс вывода из эксплуатации. Подумайте, как отслеживать жизненный цикл ADR со временем, например как переводить ADR из одного состояния в следующее и как сообщать об этом заинтересованным сторонам. 

Пример ответа: мы хотим, чтобы у ADR было пять этапов жизненного цикла: Инициирование → Исследование → Оценка → Реализация → Сопровождение → Вывод из эксплуатации.

### Каковы критерии для этапов жизненного цикла ADR?

Рассмотрите такие области, как критерии приёмки ADR, то есть как понять, что она достаточно хороша, чтобы перейти с одного этапа жизненного цикла на следующий? Чётко ли сформулирована проблема? Рассмотрены ли альтернативы? Достаточно ли хорошо поняты и задокументированы компромиссы?
Весь ли уместный контекст на месте? Все ли уместные заинтересованные стороны вовлечены? Учтены ли все отзывы? 

Пример ответа: мы хотим, чтобы заинтересованные стороны голосовали по ADR, когда активная команда 1) завершила исследование, 2) завершила оценку, 3) опубликовала предложение ADR для заинтересованных сторон с просьбой о комментариях и сроком в одну неделю, 4) все комментарии заинтересованных сторон учтены и рассмотрены.

### Какие роли и обязанности взаимодействуют с ADR?

Рассмотрите такие роли, как инициатор, исследователь, оценщик, рецензент, утверждающий, сопровождающий и т. п. Рассмотрите такие обязанности, как общение с заинтересованными сторонами, обеспечение соответствия ожиданиям, публикация на сайте или во внутренней сети, а также периодический пересмотр работы и особенно при наступлении уместных изменений.

Пример ответа: мы хотим, чтобы у каждой ADR всегда были основной контактный человек, дополнительный контактный человек и ответственная команда; они отвечают за коммуникации, публикации, сопровождение, периодический пересмотр не реже одного раза в год и возможный вывод из эксплуатации по необходимости.

### Как управление взаимодействует с ADR?

Рассмотрите такие области, как способы работы вашей организации, любые особые требования соответствия, например правовые аспекты или аспекты, связанные с персоналом, как вы хотите обращаться с консенсусом, конфликтом и эскалацией. Есть ли области, люди или команды, которые могут иметь больше влияния на ADR, чем другие, например могут её утверждать, голосовать по ней или налагать на неё вето?

Пример ответа: управление ADR осуществляется в таком порядке приоритета: генеральный директор, технический директор, юридический директор, команда, реализующая ADR, эксперты в команде, лучше всех знающие ADD. Больше ни у кого нет полномочий по управлению, если иное не описано в ADR. 

### Какие принципы взаимодействуют с ADR?

Рассмотрите такие области, как способы работы вашей организации, включая быстрое или медленное движение, консенсус или конфликт при принятии решений, предпочтения в отношении риска или безопасности, публичное или закрытое обсуждение и т. п.

Пример ответа: мы используем принципы лидерства «склонность к действию», «не соглашайся, но выполняй», «оценки на 70% достаточно хороши для легко обратимых и легко изолируемых решений» и публичные способы работы, за исключением конфиденциальной информации, как описано в соглашении о конфиденциальности нашей организации.

## Концепции следующего шага для ADR

[Arc42](https://arc42.org/) прагматично отвечает на два вопроса и может быть адаптирован под ваши потребности. Что следует документировать/доносить об архитектуре? Как следует документировать/доносить? Arc42 включает записи архитектурных решений, а также рекомендации по целям, ограничениям, контекстам, качеству, рискам и многому другому.

[Модель C4](https://c4model.com/) — простой в освоении подход к построению диаграмм программной архитектуры, удобный для разработчиков. C4 — это набор иерархических диаграмм для контекста, контейнеров, компонентов и кода, а также вспомогательные диаграммы для ландшафта систем, динамики и развёртывания.

## Архитектурные диаграммы, представления и точки зрения

Архитектурная диаграмма называется «архитектурным представлением».

«Архитектурное представление» — это экземпляр «архитектурной точки зрения».

«Архитектурная точка зрения» учитывает определённую аудиторию с определёнными интересами.

Примеры архитектурных точек зрения, представлений и диаграмм:

- Бизнес-возможности

- Бизнес-процессы высокого уровня

- [Потоки создания ценности](https://en.wikipedia.org/wiki/Value_stream)

- Программные функции, сопоставленные с компонентами приложения

- [C4 Model](https://en.wikipedia.org/wiki/C4_model) Контекстная диаграмма (TO-BE / AS-IS)

- [C4 Model](https://en.wikipedia.org/wiki/C4_model) Диаграмма контейнеров (TO-BE / AS-IS)

- [Диаграмма «сущность — связь»](https://en.wikipedia.org/w/index.php?title=Entity_relationship_diagram) (ERD) для сопоставления сущностей данных с компонентами приложения

- [Диаграммы последовательности](https://en.wikipedia.org/wiki/Sequence_diagram) для описания функциональных потоков внутри систем и при интеграциях

- [Нотация и модель бизнес-процессов](https://en.wikipedia.org/wiki/Business_Process_Model_and_Notation) (BPMN) диаграммы для описания потоков данных между компонентами приложения

- [Нотация и модель бизнес-процессов](https://en.wikipedia.org/wiki/Business_Process_Model_and_Notation) (BPMN) диаграммы для описания бизнес-процессов / пользовательских сценариев

- [Управление идентификацией и доступом](https://en.wikipedia.org/wiki/Identity_and_access_management) (IAM) диаграммы

- [Ролевое управление доступом](https://en.wikipedia.org/wiki/Role-based_access_control) (RBAC) диаграммы с ролями для каждого компонента приложения

- [Атрибутное управление доступом](https://en.wikipedia.org/wiki/Attribute-based_access_control) (ABAC) диаграммы с атрибутами для каждого компонента приложения

- Диаграммы конфиденциальности

Связанные диаграммы:

- Диаграмма вариантов использования показывает руководству/клиентам варианты использования; она предшествует требованиям, которые предшествуют программной архитектуре.

- Диаграмма развёртывания показывает физическое оборудование/компьютеры, на которые развёртываются программные компоненты.
- Диаграмма потоков данных показывает, как данные перемещаются по системе и преобразуются.
- Диаграмма последовательности используется, чтобы показать, как протоколы вроде HTTP работают на временной оси.

- Диаграмма деятельности изображает рабочий процесс действий, выполняемых программной системой, например ИИ NPC.

## Фитнес-функции для решений как код

Фитнес-функции — это объективные автоматизированные проверки, написанные программным кодом, которые подтверждают, что решения соблюдаются.

- Фитнес-функции делают решения проверяемыми и гарантируемыми.

- Фитнес-функции для решений могут сильно помочь обеспечению качества, регуляторным процессам и целям управления.

### Как фитнес-функции связаны с решениями

Запись решения документирует решение, а фитнес-функция его гарантирует.

- Пример решения: мы используем event sourcing для требований аудита.

- Пример фитнес-функции: мы используем сервер непрерывной интеграции, чтобы проверять, что все изменения состояния обязаны порождать события.

### Чем фитнес-функции помогают решениям

Объективные измерения: фитнес-функции проходят или не проходят, поэтому работа видна и понятна.

Постоянное использование: фитнес-функции — ваши живые правила, которые запускаются при каждом коммите и сборке.

Уверенность при рефакторинге: фитнес-функции автоматически выявляют ошибки в правилах решений.

Масштабируемое управление: фитнес-функции обеспечивают соблюдение стандартов, не создавая узких мест.

### Могут ли фитнес-функции использовать ИИ?

Фитнес-функции могут использовать большие языковые модели (LLM) для решений, задавая вопросы о вашей работе,
например о планах, коде, схемах, API и многом другом:

```txt
IMPORTANT: Prefer retrieval-led reasoning over pre-training-led reasoning.
IMPORTANT: Turn on extended thinking. Turn on expert advice. Turn on search.

This is a fitness function to evaluate if our work is
using all our decisions, and is correct and accurate.

- Our decisions are here: {url}
- Our work to evaluate is here: {url}

Explain any errors, problems, gaps, weaknesses. Be direct. Be decisive.
```

### Модульное тестирование архитектуры

[ArchUnit](https://www.archunit.org/): проверяйте архитектурные правила кода на Java с помощью любого обычного фреймворка модульного тестирования Java.

[ArchUnitTS](https://github.com/LukasNiessen/ArchUnitTS): проверяйте архитектурные правила кода на TypeScript и JavaScript с помощью Jest, Vitest, Jasmine и т. д.

## Ограничители решений для pull request

[Decision Guardian](https://github.com/DecispherHQ/decision-guardian)
автоматически показывает нужные записи решений в нужный момент, а именно когда
разработчик изменяет код, к которому относятся эти решения. Вместо того чтобы надеяться, что разработчики
прочитают папку с документами перед слиянием, нужный контекст появляется прямо в pull request.

Это работает для любых записей решений: архитектурных решений, решений по данным, решений по соответствию требованиям, клинических и медицинских решений, решений по безопасности и других.

Работает с любой системой CI (GitLab, Jenkins, CircleCI) и как pre-commit-хук.
Открытый исходный код. Лицензия MIT.

[ADR Guard](https://github.com/chohan-sarmad-ali/delivery-gates) — это GitHub
Action, который завершает pull request ошибкой, когда отслеживаемые пути кода меняются без добавления или обновления
записи архитектурного решения. Исключения явные: строка
`ADR-Exempt:` с причиной пропускает проверку и записывается в сводку задания. Не зависит от шаблона, без зависимостей. Открытый исходный код. Лицензия MIT.
