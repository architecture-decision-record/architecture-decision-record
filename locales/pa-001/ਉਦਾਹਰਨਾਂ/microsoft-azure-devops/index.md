## ਸਾਰ


### ਮੁੱਦਾ

ਅਸੀਂ ਆਪਣੇ ਪ੍ਰੋਜੈਕਟਾਂ ਨੂੰ ਬਿਲਡ ਕਰਨ, ਏਕੀਕ੍ਰਿਤ ਕਰਨ, ਡਿਪਲਾਇ ਕਰਨ ਅਤੇ ਹੋਸਟ ਕਰਨ ਲਈ devops ਵਰਤਣਾ ਚਾਹੁੰਦੇ ਹਾਂ। ਅਸੀਂ Microsoft Azure DevOps ਬਾਰੇ ਵਿਚਾਰ ਕਰ ਰਹੇ ਹਾਂ।

  * ਅਸੀਂ ਚਾਹੁੰਦੇ ਹਾਂ ਕਿ devops ਦੀ ਸਥਾਪਨਾ, ਜਿਵੇਂ ਕਿ ਸੰਰਚਨਾ ਕਰਨ, ਅਤੇ ਚੱਲ ਰਹੀ ਵਰਤੋਂ, ਜਿਵੇਂ ਕਿ ਤੇਜ਼ ਬਿਲਡ ਸਮੇਂ, ਲਈ ਡਿਵੈਲਪਰ ਤਜਰਬਾ ਤੇਜ਼ ਅਤੇ ਭਰੋਸੇਯੋਗ ਹੋਵੇ।
  
  * ਅਸੀਂ ਪ੍ਰੋਜੈਕਟ ਦੀਆਂ ਐਪਾਂ, ਡਾਟਾਬੇਸਾਂ ਆਦਿ ਦੀ ਹੋਸਟਿੰਗ ਲਈ Microsoft Azure ਨੂੰ ਸਮੁੱਚੇ ਤੌਰ ਉੱਤੇ ਵਰਤਣ ਬਾਰੇ ਵਿਚਾਰ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹਾਂ।


### ਫੈਸਲਾ

Microsoft Azure DevOps ਦੇ ਵਿਰੁੱਧ ਫੈਸਲਾ ਕੀਤਾ।


### ਸਥਿਤੀ

ਤੈਅ ਹੋਇਆ। ਜੇ/ਜਦੋਂ ਨਵੀਂ ਮਹੱਤਵਪੂਰਨ ਜਾਣਕਾਰੀ ਆਵੇ ਤਾਂ ਮੁੜ ਵਿਚਾਰ ਕਰਨ ਲਈ ਖੁੱਲ੍ਹੇ ਹਾਂ।


## ਵੇਰਵੇ


### ਧਾਰਨਾਵਾਂ

ਸਾਰੀਆਂ ਆਮ devops ਧਾਰਨਾਵਾਂ, ਜਿਵੇਂ ਕਿ ਕਿਤਾਬ Accelerate ਵਿੱਚ।

  * ਤੇਜ਼ ਬਿਲਡ ਇੱਕ ਮਹੱਤਵਪੂਰਨ ਮਦਦ ਹਨ। ਇਹ ਪ੍ਰਤੀਕਿਰਿਆ ਚੱਕਰਾਂ ਨੂੰ ਤੇਜ਼ ਕਰਦੇ ਹਨ।

  * ਅਸੀਂ ਵਿਕਲਪਕ ਵਿਕਰੇਤਾਵਾਂ ਦੇ ਹਿੱਸੇ ਅੰਦਰ/ਬਾਹਰ ਬਦਲ ਸਕਦੇ ਹਾਂ, ਯਾਨੀ ਅਸੀਂ ਆਪਣੇ ਵੱਧ ਗਤੀ ਵਾਲੇ ਬਿਲਡ ਸਰਵਰ ਲਿਆਉਣੇ ਚਾਹ ਸਕਦੇ ਹਾਂ, ਜਾਂ ਵਰਜਨ ਕੰਟਰੋਲ ਸਿਸਟਮ ਦੀ ਆਪਣੀ ਚੋਣ ਵਰਤਣੀ ਚਾਹ ਸਕਦੇ ਹਾਂ, ਜਾਂ ਆਪਣੇ ਹੋਸਟ ਕੀਤੇ ਨਿਰੰਤਰ ਏਕੀਕਰਨ ਸਰਵਰ ਨਾਲ ਤਾਲਮੇਲ ਕਰ ਸਕਦੇ ਹਾਂ।
  
  * ਸੁਚਾਰੂ ਵਰਤੋਂਯੋਗਤਾ ਇੱਕ ਮਹੱਤਵਪੂਰਨ ਮਦਦ ਹੈ, ਡਿਵੈਲਪਰ ਤਜਰਬੇ ਲਈ, ਅਤੇ ਬਦਲੇ ਵਿੱਚ ਇਕਸਾਰਤਾ, ਸਪੱਸ਼ਟਤਾ, ਸੁਰੱਖਿਆ ਅਤੇ ਸਿੱਖਣ ਦੇ ਵਕਰ ਦੀ ਸੌਖ ਵਰਗੇ ਬਾਰੀਕ ਖੇਤਰਾਂ ਲਈ।

  * ਜਦੋਂ ਵੀ ਕੁਝ ਟੁੱਟਿਆ ਜਾਂ ਸਮੱਸਿਆ ਵਾਲਾ ਹੋਵੇ, ਅਸੀਂ ਮਸਲੇ ਦੀ ਰਿਪੋਰਟ ਕਰਨ ਦਾ ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਤਰੀਕਾ ਚਾਹੁੰਦੇ ਹਾਂ। ਇਹ ਸੁਰੱਖਿਆ ਨਾਲ ਸੰਬੰਧਿਤ ਕਿਸੇ ਵੀ ਮਸਲੇ ਲਈ ਖਾਸ ਤੌਰ ਉੱਤੇ ਮਹੱਤਵਪੂਰਨ ਹੈ।


### ਬੰਦਸ਼ਾਂ

ਕੋਈ ਜਾਣੀ ਨਹੀਂ। Azure ਨੇ ਬਾਹਰੀ ਟੂਲਾਂ ਨਾਲ ਚੰਗੀ ਤਰ੍ਹਾਂ ਚੱਲਣ ਦੀ ਪ੍ਰਕਾਸ਼ਿਤ ਵਚਨਬੱਧਤਾ ਕੀਤੀ ਹੈ।


### ਪੱਖ

ਅਸੀਂ Microsoft Azure Devops ਬਨਾਮ AWS, ਜੋ ਪਹਿਲਾਂ ਤੋਂ ਵਰਤੋਂ ਵਿੱਚ ਹੈ, ਬਾਰੇ ਵਿਚਾਰ ਕੀਤਾ।

ਅਸੀਂ Azure DevOps, Azure Pipelines, Azure Repo ਅਤੇ Terraform ਰਾਹੀਂ ਨਵੇਂ ਸਰਵਰ ਦੀ Azure ਸ਼ੁਰੂਆਤ ਨਾਲ ਪ੍ਰਯੋਗ ਕੀਤੇ।

ਅਸੀਂ Microsoft ਦੇ ਨੁਮਾਇੰਦਿਆਂ ਤੋਂ ਸਹਾਇਤਾ ਲੈਣ ਨਾਲ ਪ੍ਰਯੋਗ ਕੀਤਾ।

ਅਸੀਂ ਬਲੌਗਾਂ ਅਤੇ Hacker News ਉੱਤੇ ਸਾਥੀਆਂ ਤੋਂ ਜਾਣਕਾਰੀ ਇਕੱਠੀ ਕੀਤੀ।


### ਦਲੀਲ

Azure DevOps ਪੇਸ਼ਕਸ਼ਾਂ ਦਾ ਸ਼ਾਨਦਾਰ ਸਮੂਹ ਇਸ਼ਤਿਹਾਰ ਕਰਦਾ ਹੈ, ਪਰ ਉਹ ਖਰੀਆਂ ਨਹੀਂ ਉਤਰਦੀਆਂ, ਉਹ ਇਕੱਠੀਆਂ ਚੰਗੀ ਤਰ੍ਹਾਂ ਕੰਮ ਨਹੀਂ ਕਰਦੀਆਂ, ਅਤੇ ਸਹਾਇਤਾ ਮਾੜੀ ਹੈ।

ਸਾਡਾ ਆਪਣਾ ਸਿੱਧਾ ਤਜਰਬਾ:

  * Azure ਦੀ ਸਥਾਪਨਾ UI ਦੀ ਗੜਬੜ ਹੈ, ਜਿਨ੍ਹਾਂ ਵਿੱਚੋਂ ਕੁਝ Microsoft ਖਾਤਿਆਂ ਨਾਲ ਓਵਰਲੈਪ ਕਰਦੇ ਹਨ ਅਤੇ ਕੁਝ ਨਹੀਂ। ਉਦਾਹਰਨ ਲਈ, Azure ਸਾਈਨ ਇਨ ਹੈ, Microsoft.com ਸਾਈਨ ਇਨ ਹੈ, Live.com ਸਾਈਨ ਇਨ ਹੈ, ਆਦਿ ਅਤੇ ਸਾਰੇ ਇੱਕੋ ਸਮੇਂ ਚੱਲ ਰਹੇ ਹਨ।

  * ਸਥਾਪਨਾ ਦੌਰਾਨ ਸਾਨੂੰ ਇੱਕ ਮਾਮੂਲੀ ਸੁਰੱਖਿਆ ਮਸਲਾ ਮਿਲਿਆ, ਅਤੇ ਕੋਈ ਹੱਲ ਨਹੀਂ ਮਿਲਿਆ। ਅਸੀਂ ਇਸ ਦੀ ਰਿਪੋਰਟ ਕਰਨ ਦੇ ਕਈ ਤਰੀਕੇ ਅਜ਼ਮਾਏ, Microsoft ਦੇ ਕਈ ਨੁਮਾਇੰਦਿਆਂ ਨੂੰ, ਬਿਨਾਂ ਸਫਲਤਾ ਦੇ। ਅਸੀਂ ਸਫਲਤਾ ਨਾਲ Microsoft ਸੁਰੱਖਿਆ ਨੂੰ ਇਸ ਦੀ ਰਿਪੋਰਟ ਕੀਤੀ, ਜਿਸ ਨੇ ਜਵਾਬ ਦਿੱਤਾ ਕਿ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾਵੇਗਾ (won't fix)।

  * ਦਸਤਾਵੇਜ਼ ਅਕਸਰ ਜਾਂ ਤਾਂ ਗਲਤ ਹੁੰਦੇ ਹਨ ਜਾਂ ਪੁਰਾਣੇ। ਇਸ ਵਿੱਚੋਂ ਘੱਟੋ-ਘੱਟ ਕੁਝ Microsoft ਦੇ ਮਾੜੇ ਖੋਜ ਇੰਜਣ ਕਾਰਨ ਹੈ, ਅਤੇ ਕੁਝ ਔਸਤ ਤੋਂ ਹੇਠਾਂ SEO ਕਾਰਨ।
  
  * Terraform ਦੀ ਸਥਾਪਨਾ ਚੰਗੀ ਤਰ੍ਹਾਂ ਦਸਤਾਵੇਜ਼ੀ ਹੈ, ਅਤੇ ਕੰਮ ਕਰਦੀ ਹੈ। ਫਿਰ ਵੀ, AWS ਦੇ ਮੁਕਾਬਲੇ Terraform ਦੀ ਸਹਾਇਤਾ ਕਮਜ਼ੋਰ ਹੈ ਕਿਉਂਕਿ Microsoft ਸ਼ੁਰੂ-ਤੋਂ-ਅੰਤ ਤੱਕ Terraform ਸਥਾਪਨਾ ਦੀਆਂ ਉਦਾਹਰਨਾਂ ਦੇਣ ਲਈ ਵਿਕਰੇਤਾਵਾਂ ਨਾਲ ਕਾਰੋਬਾਰੀ ਸੰਬੰਧ ਬਣਾ ਰਿਹਾ ਹੈ।

ਸਾਡੇ ਸਾਥੀਆਂ ਦੇ ਤਜਰਬੇ:

  * ਆਪਣਾ ਖੁਦ ਦਾ ਅੰਨ੍ਹਾ ਮੁਲਾਂਕਣ ਕਰਨ ਤੋਂ ਬਾਅਦ, ਅਸੀਂ ਸਾਥੀਆਂ ਦੇ ਤਜਰਬੇ ਲੱਭੇ। ਜੋ ਸਾਨੂੰ ਮਿਲਿਆ ਉਸ ਨੇ ਸਾਡੇ ਤਜਰਬਿਆਂ ਦੀ ਪੁਸ਼ਟੀ ਕੀਤੀ।

  * ਸਾਥੀਆਂ ਨੇ ਬਿਲਡ ਸਮਿਆਂ ਨਾਲ ਵਾਧੂ ਸਮੱਸਿਆਵਾਂ, ਅਤੇ ਆਪਣਾ-ਬਿਲਡ-ਸਰਵਰ-ਲਿਆਓ ਨਾਲ ਸਮੱਸਿਆਵਾਂ ਦੱਸੀਆਂ। ਇਹ ਸਮੱਸਿਆਵਾਂ UI ਦੀਆਂ ਸਮੱਸਿਆਵਾਂ ਨਾਲੋਂ ਕਾਫ਼ੀ ਜ਼ਿਆਦਾ ਗੰਭੀਰ ਹਨ, ਕਿਉਂਕਿ ਬਿਲਡ ਕਰਨਾ ਬਿਲਡ ਪਾਈਪਲਾਈਨ ਦਾ ਮੁੱਖ ਉਦੇਸ਼ ਹੈ, ਅਤੇ ਅਸੀਂ ਰੋਜ਼ਾਨਾ ਕਈ ਬਿਲਡ ਕਰਨ ਦੀ ਉਮੀਦ ਕਰਦੇ ਹਾਂ।

  * ਸਾਨੂੰ ਚਰਚਾ ਦੇ ਖੇਤਰਾਂ ਵਿੱਚ Azure ਦੇ ਸਾਥੀਆਂ ਦੀ ਸ਼ਾਨਦਾਰ ਸ਼ਮੂਲੀਅਤ ਮਿਲੀ। ਇਸ ਲਈ Microsoft ਦੀ ਸ਼ਲਾਘਾ। ਅਸੀਂ Azure PM ਅਤੇ ਕੋਡਰ Edward Thomson ਦੀ ਸ਼ਮੂਲੀਅਤ, ਸਿੱਧੇਪਣ ਅਤੇ ਤਕਨੀਕੀ ਵਿਆਖਿਆਵਾਂ ਕਾਰਨ ਖਾਸ ਤੌਰ ਉੱਤੇ ਪ੍ਰਭਾਵਿਤ ਹਾਂ।


### ਪ੍ਰਭਾਵ

Microsoft Azure DevOps ਚੁਣਨਾ Azure ਨਾ ਚੁਣਨ ਨਾਲੋਂ ਸਮੇਂ ਅਤੇ ਲਾਗਤ ਵਿੱਚ ਵਧੇਰੇ ਮਹਿੰਗਾ (~3 ਗੁਣਾ) ਹੋਣ ਦੀ ਸੰਭਾਵਨਾ ਹੈ।


## ਸੰਬੰਧਿਤ


### ਸੰਬੰਧਿਤ ਫੈਸਲੇ

ਜੇ ਅਸੀਂ Azure DevOps ਚੁਣਦੇ ਹਾਂ, ਤਾਂ Azure Repo, Azure Pipeline ਆਦਿ ਸਮੇਤ ਕਈ ਸੰਬੰਧਿਤ ਪੇਸ਼ਕਸ਼ਾਂ ਹਨ। ਸਾਡਾ ਮੰਨਣਾ ਹੈ ਕਿ ਜੇ ਅਸੀਂ Azure Devops ਚੁਣਦੇ ਹਾਂ, ਤਾਂ ਇਹ ਹੋਰ Azure ਸਮਰੱਥਾਵਾਂ ਵਰਤਣਾ ਆਸਾਨ ਬਣਾ ਸਕਦਾ ਹੈ, ਜਾਂ ਹੋਰ ਵਿਕਰੇਤਾਵਾਂ ਦੀਆਂ ਸਮਰੱਥਾਵਾਂ ਵਰਤਣਾ ਔਖਾ ਬਣਾ ਸਕਦਾ ਹੈ।

ਸਾਡਾ ਮੰਨਣਾ ਹੈ ਕਿ Microsoft ਡਿਵੈਲਪਰ ਤਜਰਬੇ ਵਿੱਚ ਵੱਡੀਆਂ ਪੁਲਾਂਘਾਂ ਪੁੱਟ ਰਿਹਾ ਹੈ, ਅਤੇ ਅਸੀਂ ਵੇਖਦੇ ਹਾਂ ਕਿ Microsoft ਡਿਵੈਲਪਰ ਟੂਲਾਂ (ਜਿਵੇਂ ਕਿ GitHub) ਅਤੇ ਨਿਰਭਰਤਾਵਾਂ (ਜਿਵੇਂ ਕਿ Citus) ਦੀਆਂ ਵੱਡੀਆਂ ਪ੍ਰਾਪਤੀਆਂ ਕਰ ਰਿਹਾ ਹੈ।

ਜੇ ਅਸੀਂ Azure DevOps ਚੁਣਦੇ ਹਾਂ, ਤਾਂ ਅਸੀਂ Microsoft ਦੀਆਂ ਪ੍ਰਾਪਤ ਕੀਤੀਆਂ ਪੇਸ਼ਕਸ਼ਾਂ ਚੁਣਨ ਉੱਤੇ ਜ਼ੋਰ ਦੇਣਾ ਚਾਹ ਸਕਦੇ ਹਾਂ, ਅਤੇ ਅਸੀਂ ਸੰਭਾਵੀ ਟਿਸ਼ੂ-ਅਸਵੀਕਾਰ, ਜਿਵੇਂ ਕਿ ਸਟਾਫ ਦੇ ਛੱਡ ਜਾਣ ਦੇ ਜੋਖਮ, ਕਾਰਨ ਪ੍ਰਾਪਤ ਪੇਸ਼ਕਸ਼ਾਂ ਨੂੰ ਵਧੇਰੇ ਸਾਵਧਾਨੀ/ਮੁਲਾਂਕਣ ਨਾਲ ਅਪਣਾਉਣਾ ਵੀ ਚਾਹ ਸਕਦੇ ਹਾਂ।


### ਸੰਬੰਧਿਤ ਲੋੜਾਂ

ਅਸੀਂ ਚਾਹੁੰਦੇ ਹਾਂ ਕਿ ਬਿਲਡ ਸਮੇਂ ਬਹੁਤ ਤੇਜ਼ ਹੋਣ। ਅਸੀਂ ਇਸ ਲਈ ਉੱਚਾ ਪ੍ਰੀਮੀਅਮ ਦੇਣਾ ਸਵੀਕਾਰ ਕਰਦੇ ਹਾਂ। ਇਹ ਇਸ ਲਈ ਹੈ ਕਿਉਂਕਿ ਅਸੀਂ ਬਹੁਤ ਤੇਜ਼ੀ ਨਾਲ ਦੁਹਰਾਓ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹਾਂ।

ਅਸੀਂ ਚਾਹੁੰਦੇ ਹਾਂ ਕਿ ਭਰੋਸੇਯੋਗਤਾ ਬਹੁਤ ਉੱਚੀ ਹੋਵੇ। ਅਸੀਂ ਇਸ ਲਈ ਉੱਚਾ ਪ੍ਰੀਮੀਅਮ ਦੇਣਾ ਸਵੀਕਾਰ ਕਰਦੇ ਹਾਂ। ਇਹ ਇਸ ਲਈ ਹੈ ਕਿਉਂਕਿ ਅਸੀਂ ਵਿੱਤੀ ਲੈਣ-ਦੇਣ, ਗੁਪਤ ਲੈਣ-ਦੇਣ ਆਦਿ ਸਮੇਤ ਉੱਚ-ਮੁੱਲ ਵਾਲੇ ਵਰਤੋਂ ਦੇ ਕੇਸਾਂ ਦੀ ਜਾਂਚ ਕਰ ਰਹੇ ਹਾਂ।

ਸਾਡੇ ਸਿਖਰਲੇ 4 devops KPI ਵਿੱਚ ਰਿਕਵਰੀ ਦਾ ਔਸਤ ਸਮਾਂ ਸ਼ਾਮਲ ਹੈ, ਜਿਸ ਲਈ ਤੇਜ਼ ਬਿਲਡ ਅਤੇ ਉੱਚ ਭਰੋਸੇਯੋਗਤਾ ਜ਼ਰੂਰੀ ਹਨ।

### Windows Development MVP

ਇੱਥੇ Windows Development MVP ਬੋਲ ਰਿਹਾ ਹਾਂ। ਮੈਨੂੰ ਲੱਗਦਾ ਹੈ ਕਿ ਮੈਨੂੰ ਇਨ੍ਹਾਂ ਮਸਲਿਆਂ ਬਾਰੇ ਵਧੇਰੇ ਉੱਚੀ ਨਾ ਬੋਲਣ ਦੀ ਕੁਝ ਜ਼ਿੰਮੇਵਾਰੀ ਆਪਣੇ ਸਿਰ ਲੈਣੀ ਚਾਹੀਦੀ ਹੈ। ਪਰ ਇਹ ਜ਼ਰੂਰ ਕਹਾਂਗਾ ਕਿ ਮੈਂ ਨਿਰਾਸ਼ ਹਾਂ ਕਿ ਤੁਸੀਂ UX ਮਸਲਿਆਂ ਤੋਂ "ਹੈਰਾਨ" ਹੋ। ਮੈਂ ਤੁਹਾਡੇ ਲੋਕਾਂ ਨੂੰ ਕਹਿੰਦਾ ਰਿਹਾ ਹਾਂ ਕਿ UX ਭਿਆਨਕ ਹੈ (ਜਿਵੇਂ ਕਿ ਲਾਂਚ ਤੋਂ ਪਹਿਲਾਂ ਤੱਕ ਵੀ) ਅਤੇ ਮੈਨੂੰ ਇਹੀ ਜਵਾਬ ਮਿਲਦਾ ਰਿਹਾ ਕਿ "ਸਾਨੂੰ ਪਤਾ ਹੈ, ਅਸੀਂ ਠੀਕ ਕਰ ਰਹੇ ਹਾਂ"। ਮੈਂ ਪ੍ਰਤੀਕਿਰਿਆ ਨੂੰ ਰਸਮੀ ਰੂਪ ਦੇਣਾ ਸ਼ੁਰੂ ਕਰਾਂਗਾ ਅਤੇ ਇਸ ਨੂੰ ਪਾਈਪਾਂ ਰਾਹੀਂ ਅੱਗੇ ਭੇਜਾਂਗਾ, ਜੁੜੇ ਰਹੋ। ਮੈਂ ਸਥਾਨਕ (Bellevue) ਵੀ ਹਾਂ, ਅੰਦਰ ਆ ਕੇ ਆਪਣੀ ਮੁਕਾਬਲਤਨ ਸਾਦੀ oss .net/wpf/uwp ਐਪ ਨੂੰ ਪਾਈਪਲਾਈਨ ਵਿੱਚ ਪਾਉਣ ਦੀ ਕੋਸ਼ਿਸ਼ ਕਰਨਾ ਚਾਹਾਂਗਾ। ਮੈਨੂੰ ਸ਼ੱਕ ਹੈ ਕਿ ਇਹ ਸਾਡੇ ਦੋਵਾਂ ਦੀਆਂ ਅੱਖਾਂ ਖੋਲ੍ਹੇਗਾ।

ਕੁਝ ਉਦਾਹਰਨਾਂ:

* ਤੁਸੀਂ ਸਬਮੌਡਿਊਲਾਂ ਵਾਲੇ git ਰਿਪੋ ਨਾਲ ਪਾਈਪਲਾਈਨ ਨਹੀਂ ਬਣਾ ਸਕਦੇ

* ਕੁਝ ਕਸਟਮ ਟੂਲਿੰਗ ਲਈ PATH ਨੂੰ ਸੰਪਾਦਿਤ ਕਰਨਾ ਅਸੰਭਵ ਲੱਗਾ

* ਨਵੀਂ ਪਾਈਪਲਾਈਨ ਦਾ ਤਜਰਬਾ ਬਸ ਬਹੁਤਾ ਸਮਝ ਨਹੀਂ ਆਉਂਦਾ, ਨਵੇਂ ਵਰਤੋਂਕਾਰ ਇੱਧਰ-ਉੱਧਰ ਕਲਿੱਕ ਕਰਦੇ ਆਖ਼ਰਕਾਰ ਗਲਤ ਦਸਤਾਵੇਜ਼ਾਂ ਉੱਤੇ ਪਹੁੰਚ ਜਾਂਦੇ ਹਨ।
